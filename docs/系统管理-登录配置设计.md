## 1. 目标与划界

一句话：**登录管线是"执行代码"，登录配置是"策略数据"，本文只管策略怎么存、怎么校验、怎么生效。**

| | 管登录管线的文档 | 本文 |
|---|---|---|
| 回答的问题 | 一次登录请求怎么走完 | 管线各环节的参数从哪来、谁来改 |
| 变更频率 | 上线后基本不动 | 管理员随时调整 |

两个配置类型：

| config_type | 名称 | 说明 |
|---|---|---|
| 1 | 管理后台登录 | 平台运营方 `sys_user`，安全策略取最严 |
| 2 | 租户登录 | 企业客户 `hr_account`，策略可适度放宽 |

**设计判断：每类型一行全局配置，不做按租户覆盖。** 理由：租户侧各自定制登录策略（A 租户要短信、B 租户要邮箱）意味着配置行 = 租户数，且登录路径变成运行时分支矩阵。一期用 `scope_id` 预留列（0=全局），真有"按租户覆盖"需求时再启用，届时只加不改。

不做清单：登录时段限制、登录 IP 白名单、按租户覆盖配置（均只留扩展位）。

## 2. 配置项清单

分三组：登录组件（能怎么登）、账号保护（错了怎么办）、会话与密码（登进去之后管什么）。参照阿里云 RAM 安全设置补全，文末 §2.4 给对照表。

### 2.1 登录组件开关（login_mask 位掩码）

| 位 | 值 | 组件 | 说明 |
|---|---|---|---|
| bit0 | 1 | 账号 + 密码 | username_password，管理后台的保底方式 |
| bit1 | 2 | 手机 + 密码 | mobile_password，与 bit0 共用密码因子 |
| bit2 | 4 | 手机 + 短信 | mobile_sms，依赖短信通道 |
| bit3 | 8 | 邮箱 + 密码 | email_password，租户侧常见 |
| bit4~bit7 | 16/32/64/128 | 预留 | SSO / TOTP 独立因子 / 扫码 / 微信 |

三条纪律（与 i18n 的 lang_mask 同一套玩法）：

1. **只在掩码里增位，不改已有位的含义**；废弃组件保留位号、标记禁用。
2. **校验规则：掩码 ≠ 0（至少启用一种）**。
3. **admin 配置必须保留 bit0（账号+密码）**。超管账号"必须密码登录"是 sys_user 文档 §8.3 的硬约束——如果 admin 配置允许关掉密码登录，短信通道一故障平台就失管了。这条是**服务端校验拒绝**，不是前端提示。

前端登录页根据 `login_mask` 动态渲染可用的登录 tab（掩码=0 的组件不显示输入入口）；但接口侧**必须独立校验**——前端隐藏只是体验，组件关闭时对应登录接口返回"该登录方式未开放"，防止直接调接口绕过。

### 2.2 账号保护（参考阿里云 + sys_user §6 现状参数化）

| 配置项 | 字段 | 默认值 | 取值范围 | 说明 |
|---|---|---|---|---|
| 错误登录次数阈值 | `fail_threshold` | 5 | 3~20 | 连续密码/短信码错误 N 次触发冻结 |
| 冻结时长（分钟） | `lock_minutes` | 15 | 1~1440 | 超过 1440 分钟建议走"管理员手动解锁" |
| 解锁方式 | `unlock_mode` | 3 | 1 自动到期 / 2 仅管理员 / 3 两者皆可 | |
| 触发图形验证码的失败次数 | `captcha_after_fails` | 3 | 0=关闭 / 2~5 | 密码登录连续失败 N 次后强制图形码（sys_user §8.7 参数化） |
| 单 IP 登录失败限流（次/小时） | `ip_fail_limit` | 50 | 10~1000 | 撞库兜底，sys_user §6 的 IP 分桶参数化 |
| 单 IP 登录请求限流（次/分钟） | `ip_rate_limit` | 20 | 5~600 | sys_user §8.6 参数化 |

要点：**`fail_threshold` 与 `lock_minutes` 是一对，改小阈值时必须同步检查冻结时长**——错 20 次才锁 1440 分钟，或错 3 次只锁 1 分钟，都是失效的策略组合。校验规则：`lock_minutes ≥ fail_threshold × 2`（分钟数），防止"又松又短"。

### 2.3 会话与 Token

| 配置项 | 字段 | 默认值 | 取值范围 | 说明 |
|---|---|---|---|---|
| accessToken 有效期（秒） | `access_token_ttl` | 7200 | 300~86400 | JWT exp + Redis 会话 TTL |
| refreshToken 有效期（秒） | `refresh_token_ttl` | 604800 | 3600~2592000 | 硬上限 30 天 |
| 硬上限（硬过期，秒） | `session_hard_ttl` | 86400 | ≥ access_token_ttl | 对应 sys_user §7 "硬上限 24h"：会话无论怎么滑动续期，超过它必须重新登录 |
| 同账号最大并发会话 | `session_max_concurrent` | 3 | 0=不限 / 1~10 | 超出时挤掉最早的会话 |
| 修改密码是否踢下线 | `kick_on_pwd_change` | 1 | 0/1 | sys_user §7 默认行为，参数化后可关（租户侧慎关） |
| 记住登录状态 | `remember_days` | 0 | 0~30 | 对应阿里云"保存登录状态 7 天"：登录页勾选后 refreshToken 按此天数放宽 |

校验规则：

- `access_token_ttl < refresh_token_ttl`（短期的没理由比长期的还长）；
- `session_hard_ttl ≥ refresh_token_ttl`（refresh 生命期不能超过会话硬上限，否则"硬上限"名存实亡）；
- `remember_days ≤ refresh_token_ttl / 86400`。

### 2.4 密码复杂度（等级预设 + 明细字段双层）

管理界面给管理员的是**三档选择**（对齐阿里云"密码强度：低/中/高"），运行时读的是**明细字段**。保存时把预设写入明细，**明细字段是唯一真相，等级只是预设选择器**——避免"等级=高但明细是低"的两处真相问题。

| 等级 | `pwd_min_length` | `pwd_min_classes` | 附加规则 |
|---|---|---|---|
| 1 低 | 8 | 1 | 无 |
| 2 中（默认） | 10 | 2 | 不含账号名 |
| 3 高 | 12 | 3（大小写/数字/符号） | 不含账号名 + 不含 3 位以上连续/重复字符 |

明细字段（运行时唯一真相）：

| 配置项 | 字段 | 默认 | 说明 |
|---|---|---|---|
| 最小长度 | `pwd_min_length` | 10 | 8~32 |
| 最少字符类别数 | `pwd_min_classes` | 2 | 1~4（大写/小写/数字/符号） |
| 禁止包含账号名 | `pwd_forbid_username` | 1 | 含账号名/倒序即拒绝 |
| 密码有效期（天） | `pwd_max_age_days` | 0 | 0=不过期；阿里云默认 90 天，管理后台建议 180（sys_user §8.2 是"提示不强制"，配置化后由 `pwd_expire_action` 决定） |
| 到期动作 | `pwd_expire_action` | 1 | 1 提示不强制 / 2 强制改密（到期登录直接跳改密页） |
| 到期提前提醒（天） | `pwd_remind_days` | 7 | 登录响应里带 `pwd_expiring: true` |
| 历史密码重复限制 | `pwd_history_count` | 3 | 改密时不得与最近 N 次相同（存历史 hash，bcrypt 校验） |
| 首次登录强制改密 | `pwd_force_first_change` | 0 | 管理员代建账号/重置密码后置位，登录后先改密 |
| 允许自助改密 | `allow_self_change_pwd` | 1 | 对应阿里云"允许 RAM 用户自主修改密码"；关闭后只能管理员重置 |

密码策略**只对新写入生效，不追溯存量**：改严后老密码照常登录，下次修改时按新策略校验。

### 2.5 扩展项（extras JSON）

MFA 模式、登录 IP 白名单、登录时段等**一期不做**的项不建列，统一进 `extras JSON`：

```json
{ "mfa_mode": 0, "mfa_grace_days": 0, "ip_whitelist": [], "login_time_range": null }
```

理由：为不存在的需求建列是成本（sys_user 文档 §1 同一判断）；但 key 先占位，未来转正式列时迁移是"读 extras 写列"，不是数据考古。

### 2.6 阿里云 RAM 对照表

| 阿里云 RAM 安全设置 | 本文对应 | 差异说明 |
|---|---|---|
| 默认 MFA 要求 / 仅异常登录要求 | `extras.mfa_mode` | 一期预留 |
| 保存 MFA 状态 7 天 | `extras` | 同上 |
| 登录会话时长 | `access_token_ttl` | 阿里云 1~12h，本文 5min~24h |
| 保存登录状态 7 天 | `remember_days` | 放宽 refresh token |
| 密码强度（低/中/高） | `pwd_level` 预设 | 见 §2.4 双层设计 |
| 密码最小长度 / 字符类型 | `pwd_min_length` / `pwd_min_classes` | |
| 密码有效期 | `pwd_max_age_days` + `pwd_expire_action` | 阿里云仅强制，本文多一档"提示" |
| 历史密码限制 | `pwd_history_count` | |
| 首次登录修改密码 | `pwd_force_first_change` | |
| 允许用户自主修改密码 | `allow_self_change_pwd` | |
| 允许用户管理 AccessKey | 不对应 | 本系统无 AccessKey 概念 |
| 全局 IP 白名单 | `extras.ip_whitelist` | 预留 |

阿里云没有、本文补充的：错误次数与冻结时长（阿里云在账号层有，RAM 层无）、同账号并发会话数、单 IP 限流——这三项是撞库防护的主战场，不能少。

## 3. 数据模型

### 3.1 DDL

```sql
CREATE TABLE IF NOT EXISTS sys_login_config (
    id                    BIGINT       NOT NULL COMMENT '雪花ID',
    config_type           TINYINT      NOT NULL COMMENT '1管理后台登录 2租户登录',
    scope_id              BIGINT       NOT NULL DEFAULT 0 COMMENT '0=全局；预留按租户覆盖',
    login_mask            BIGINT       NOT NULL COMMENT '登录组件位掩码：1账号密码 2手机密码 4手机短信 8邮箱密码',
    fail_threshold        SMALLINT     NOT NULL DEFAULT 5 COMMENT '错误登录次数阈值',
    lock_minutes          SMALLINT     NOT NULL DEFAULT 15 COMMENT '冻结时长（分钟）',
    unlock_mode           TINYINT      NOT NULL DEFAULT 3 COMMENT '1自动到期 2仅管理员 3两者皆可',
    captcha_after_fails   SMALLINT     NOT NULL DEFAULT 3 COMMENT 'N次失败后强制图形码，0=关闭',
    ip_fail_limit         SMALLINT     NOT NULL DEFAULT 50 COMMENT '单IP登录失败限流（次/小时）',
    ip_rate_limit         SMALLINT     NOT NULL DEFAULT 20 COMMENT '单IP登录请求限流（次/分钟）',
    access_token_ttl      INT          NOT NULL DEFAULT 7200 COMMENT 'accessToken有效期（秒）',
    refresh_token_ttl     INT          NOT NULL DEFAULT 604800 COMMENT 'refreshToken有效期（秒）',
    session_hard_ttl      INT          NOT NULL DEFAULT 86400 COMMENT '会话硬上限（秒）',
    session_max_concurrent SMALLINT    NOT NULL DEFAULT 3 COMMENT '同账号最大并发会话，0=不限',
    kick_on_pwd_change    TINYINT(1)   NOT NULL DEFAULT 1 COMMENT '修改密码是否踢下线',
    remember_days         SMALLINT     NOT NULL DEFAULT 0 COMMENT '记住登录状态天数，0=关闭',
    pwd_level             TINYINT      NOT NULL DEFAULT 2 COMMENT '密码复杂度等级：1低 2中 3高（仅预设展示用）',
    pwd_min_length        SMALLINT     NOT NULL DEFAULT 10 COMMENT '最小密码长度',
    pwd_min_classes       SMALLINT     NOT NULL DEFAULT 2 COMMENT '最少字符类别数 1~4',
    pwd_forbid_username   TINYINT(1)   NOT NULL DEFAULT 1 COMMENT '禁止包含账号名',
    pwd_max_age_days      INT          NOT NULL DEFAULT 0 COMMENT '密码有效期（天），0=不过期',
    pwd_expire_action     TINYINT      NOT NULL DEFAULT 1 COMMENT '1到期提示 2到期强制改密',
    pwd_remind_days       SMALLINT     NOT NULL DEFAULT 7 COMMENT '到期提前提醒天数',
    pwd_history_count     SMALLINT     NOT NULL DEFAULT 3 COMMENT '不得与最近N次密码重复，0=不限制',
    pwd_force_first_change TINYINT(1)  NOT NULL DEFAULT 0 COMMENT '首次登录强制改密',
    allow_self_change_pwd TINYINT(1)   NOT NULL DEFAULT 1 COMMENT '允许自助改密',
    extras                JSON         NULL COMMENT '扩展项：mfa_mode/ip_whitelist 等，见 §2.5',
    version               INT          NOT NULL DEFAULT 0 COMMENT '乐观锁',
    updated_by            BIGINT       NOT NULL DEFAULT 0 COMMENT '最后修改人（审计）',
    created_at            DATETIME(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
    updated_at            DATETIME(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),
    PRIMARY KEY (id),
    UNIQUE KEY uk_config (config_type, scope_id)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4 COLLATE = utf8mb4_0900_ai_ci;
```

设计说明：

1. **单表、每类型一行**（`uk_config` 保证不重复）。总行数 ≤ 3，不存在分页、查询、归档问题，任何"配置中心化"的设计（拆 key-value 表）在这里都是过度设计。
2. **结构化列而不是全 JSON**：每个配置项都有独立的校验规则、默认值和生效点，拍平成列后"一眼看清当前生效值"；只有未实现的预留项进 `extras`。
3. **`updated_by` + `version`**：改登录策略是高危操作，谁改的要进操作日志（配合 OperLog 中间件记录 diff）；乐观锁防两个管理员并发保存互相覆盖。
4. **没有 `deleted_at` / `status`**：配置行不可删（删了管线就没有策略可读），停用语义由字段值表达（如 `login_mask` 收缩）。


> **v1.1 seed 修正说明**：§2.3 默认值表与 §6 规则 4 在 v1.0 原稿中互相矛盾
>（refresh 7 天 > 硬上限 24h）。经用户裁定"规则为准，改 seed"：两行 seed 与
> §3.3 代码兜底常量的 `refresh_token_ttl` 均改为 86400。副作用：默认配置下
> `remember_days ≤ refresh_token_ttl/86400` = 最多 1 天（规则 5）。

两个默认值的刻意差异：

- **admin 不开手机短信登录**（mask=3 非 7）：管理后台手机号是高价值情报（sys_user §5 防枚举），短信登录收益低、暴露面大。要开可以，管理员显式改。
- **admin `session_max_concurrent=1`**：管理员不该有多端并行会话；租户给 3。

### 3.3 代码兜底默认值

**配置行读不到时（表空、seed 漏跑）用代码内置默认值**，与 §3.2 的值保持同一份常量。绝不允许"读不到配置 = 全放行"：

```go
// 兜底语义是"最严默认"，不是"无配置"
func (c *Config) LoginMask() int64 {
    if c.row == nil { return DefaultLoginMask } // 不是 return math.MaxInt64
    return c.row.LoginMask
}
```

## 4. 读取与缓存

登录是最高频路径之一，但配置行 ≤ 3 行且分钟级才变一次。缓存策略：

```
进程内存缓存（30s TTL）
   ↓ miss
Redis  login:config:{config_type}   （5min TTL）
   ↓ miss
MySQL  sys_login_config（uk_config 唯一行）
```

失效规则：

1. **管理端保存成功 → 立即删 Redis 键**。进程内存缓存的 30s TTL 是唯一容忍窗口，可接受（登录策略变更不是秒级敏感操作）。
2. **读不到任何一层 → 回落代码兜底默认值**（§3.3），并告警。逻辑上"DB 挂了登录还能跑"，但跑在默认值上，管理员会看到"我改的配置没生效"——这是刻意设计：**配置读失败宁可退回保守默认，也不拒登或放行**。
3. 不用 pub/sub 广播失效：3 行配置的 stale 窗口 ≤ 30s，为它引入订阅链路不划算。

## 5. 管理接口

```
GET  /api/v1/admin/login-configs-admin        管理后台配置（写死 type=1；按前端所需字段投影，§11.2-⑩）
PUT  /api/v1/admin/login-configs/{type}       全量更新（body 带 version 乐观锁；布尔字段 0/1）
POST /api/v1/admin/login-configs/{type}/reset 恢复该类型默认值（§3.2 seed 值）
```

> **v1.3 用户裁定**：不设租户读取端——管理后台不拉租户数据；租户配置的读取随
> 租户登录模块（hr_account 管线）在 `/api/v1/tenant/*` 体系自行定义，管理端对
> type=2 仅保留 PUT/reset。
> **v1.4 用户裁定**：`GET /login-configs-admin` 加入白名单匿名可读——登录页在
> 未登录时就要按 `login_mask` 动态渲染可用的登录 tab（§2.1）；只读投影开放，
> PUT/reset 仍要求登录态。

约定：

1. **PUT 全量更新**（不是 PATCH 逐项）：配置项之间有联动校验（§6），逐项 PATCH 会出现"先改阈值触发校验失败、卡在中间态"。前端编辑弹窗一次提交整单。
2. **reset 需二次确认**：恢复默认值会把管理员的所有定制抹掉。
3. 保存成功后：删缓存 → 写操作日志（记录修改前后的 diff，OperLog `operlog.SetDiff`）→ 返回新版本号。
4. 权限：独立权限点 `system:login-config:write`——能改登录策略的人，约等于能决定"整个后台谁能进来"。

## 6. 保存校验规则（服务端，前端仅为提示）

| # | 规则 | 失败文案方向 |
|---|---|---|
| 1 | `login_mask ≠ 0` | 至少启用一种登录方式 |
| 2 | `config_type=1` 时 `login_mask & 1 ≠ 0` | 管理后台必须保留"账号+密码"登录 |
| 3 | `lock_minutes ≥ fail_threshold × 2`（分钟） | 冻结时长与错误次数不匹配，过松或过短 |
| 4 | `access_token_ttl < refresh_token_ttl ≤ session_hard_ttl` | Token 有效期层级错乱 |
| 5 | `remember_days ≤ refresh_token_ttl/86400` | 记住登录不能超过 refreshToken 有效期 |
| 6 | `pwd_min_length` 8~32；`pwd_min_classes ≤ 4` 且 ≤ `pwd_min_length`（长度至少装得下类别数） | 密码复杂度参数非法 |
| 7 | `pwd_level` 与明细字段一致性：保存时**以明细为准反推等级**回写（管理员只选了等级时，用等级预设覆盖明细；明细被单独改过时，等级自动落为最近匹配档） | — |
| 8 | extras JSON schema 校验（mfa_mode 枚举、ip_whitelist 为合法 CIDR 数组） | 扩展项格式错误 |

防呆提示（前端，不拦截）：

- 收缩 `login_mask` 前提示"当前有 N 种登录方式，关闭后使用这些方式的用户将无法登录"；
- 调低 `access_token_ttl` / 改 `kick_on_pwd_change` 时提示"对已签发的会话不生效，可到会话管理执行全端登出"。

## 7. 运行时生效点

配置改了之后在哪生效，逐项落到管线的具体位置——这张表是"配置 ↔ 管线"的对账单，漏一行就是"改了没反应"的工单来源：

| 配置项 | 生效位置 | 即时生效？ |
|---|---|---|
| `login_mask` | 登录接口入口校验 + 前端登录页 tab 渲染 | 是（缓存失效后） |
| `fail_threshold` / `lock_minutes` / `unlock_mode` | 计数锁定逻辑（sys_user §6）读取 | 是；**已冻结的账号不追溯**（`locked_until` 已落库，按被锁时的配置执行完） |
| `captcha_after_fails` | 密码登录接口的图形码前置判断 | 是 |
| `ip_fail_limit` / `ip_rate_limit` | 限流中间件 | 进程内缓存窗口内（≤30s） |
| `access_token_ttl` | JWT 签发 + Redis 会话 TTL | **仅新签发的会话**；存量会话按签发时的 TTL |
| `refresh_token_ttl` / `session_hard_ttl` | 刷新与续期逻辑 | 仅新签发 |
| `session_max_concurrent` | 登录签发时挤最早会话 | 是 |
| `kick_on_pwd_change` | 改密事件处理 | 是 |
| `remember_days` | 登录响应签发 | 是 |
| `pwd_*` 全部 | 改密/重置密码校验 | 是；存量密码不追溯（§2.4） |
| `pwd_force_first_change` | 重置密码时置位 → 登录后跳改密页 | 是 |
| `allow_self_change_pwd` | 自助改密接口入口 | 是 |
| `extras.mfa_mode` | 登录成功后二次校验环节（预留） | — |

其中三条"仅新签发生效"是容易被误解的点，管理界面要在对应字段旁显式标注"对已登录会话不生效，可执行全端登出强制生效"。

## 8. 边界情况清单

| 情况 | 处理 |
|---|---|
| 配置行不存在（seed 漏跑/表损坏） | 代码兜底默认值（§3.3）继续服务登录，同时告警；管理端展示"当前为兜底默认值"横幅 |
| DB 整体不可用 | 登录跑在缓存/兜底默认值上；管理端保存接口直接失败，绝不静默丢改动 |
| 两个管理员并发保存 | version 乐观锁，后者保存时提示刷新重试 |
| 保存成功但删缓存失败 | 缓存 TTL（5min）兜底过期；日志记 WARN |
| 关闭了某用户唯一可用的登录方式 | 用户侧登录报"该登录方式未开放"；管理员侧由 §6 规则 1/2 保证不会全关 |
| 调短 `lock_minutes` 时有账号正在冻结中 | 不追溯：该账号按被锁时的配置执行完 `locked_until` |
| `pwd_max_age_days` 从 90 改为 0（取消过期） | 存量"已到期"标记随下次登录清除 |
| 管理员把 admin 配置 reset | 恢复 §3.2 最严默认，二次确认；超管会话不受影响（已签发） |
| extras 里出现未知 key | 保留不删（向下兼容未来版本写入的配置） |

## 9. 前端交互要点

1. **配置页结构**：两个 tab（管理后台登录 / 租户登录），各自一张分组表单（登录组件 → 账号保护 → 会话与 Token → 密码策略），底部"保存 / 恢复默认"。

## 10. 实施顺序

| 阶段 | 内容 |
|---|---|
| **P0** | 建表 + seed 两行默认；配置读取（三级缓存 + 代码兜底）；接入**已有**管线的计数锁定、Token TTL、图形码触发三个生效点（sys_user 文档里的硬编码值换成读配置） |

| **P2（预留）** | MFA（extras.mfa_mode 转正式）、IP 白名单、按租户覆盖（scope_id 启用） |

P0 验收标准：**把 seed 行的 `fail_threshold` 改成 3、`lock_minutes` 改成 30，登录错 3 次会被冻 30 分钟**——这一条通了，配置到管线的链路就是活的。

> v1.1：P0/P1/P1.5 已全部落地（用户裁定"全部接入"，含 §7 其余生效点），实现细节与
> 实测记录见 §11，偏差登记见 §11.3。

P1.5 附带一张新表：

```sql
CREATE TABLE IF NOT EXISTS sys_password_history (
    id            BIGINT        NOT NULL,
    user_type     TINYINT       NOT NULL COMMENT '1 sys_user 2 hr_account',
    user_id       BIGINT        NOT NULL,
    password_hash VARCHAR(128)  NOT NULL COMMENT 'bcrypt，与主表同算法',
    created_at    DATETIME(3)   NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
    PRIMARY KEY (id),
    KEY idx_pwdhist (user_type, user_id, created_at)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4 COLLATE = utf8mb4_0900_ai_ci;
```

改密时写入旧 hash，`pwd_history_count` 校验即"逐条 bcrypt 比对最近 N 行"。只增不改，按 `created_at` 定期清理超出窗口的旧行。

### 11.2 生效点接线细节（§7 对账单的实现语义）

1. **login_mask 入口开关**：`LoginPassword` 按标识形状判定 bit0/bit1（账号名禁形似手机号，形状判定无歧义）；`LoginSms`/`SendSms` 查 bit2。关闭 → `authn.ErrLoginMethodClosed` → **30052 该登录方式未开放**。
2. **计数锁定**：`fail_threshold`/`lock_minutes` 来自快照；`unlock_mode=2`（仅管理员）时锁定写**哨兵锁**（`locked_until = now+100 年`，Redis TTL 同步）——登录响应改带 `data.unlock_by_admin=true` 不带倒计时（`ErrLocked.Remaining=-1`）；判定阈值为剩余 >30 天（自动冻结上限 24h、人工冻结上限 7 天均远小于哨兵）。已冻结账号不追溯（locked_until 已落库）。
3. **图形码**：`captcha_after_fails`（0=关闭）；阈值前不要求，达标后正确密码也先要图形码（实测 30014）。
4. **IP 限流**：`ip_rate_limit`（/min）、`ip_fail_limit`（/h）参数化进 `LoginGuard` 端口（实测第 6 次 30017）。
5. **会话**：`access_token_ttl` 进 JWT exp + Redis 键 TTL（实测新签发 7200s）；`session_hard_ttl` 进 `sess:abs:`；`session_max_concurrent` 经 `SessionStore.PruneMax` 挤最早——用户索引由 SET 升级为 **ZSET `sess:u2:{uid}`**（score=创建毫秒），KickAll/Delete 兼容两代索引；升级前创建的旧会话 ≤24h 自灭，不在并发计数内（迁移窗口，已知无害）。
6. **`remember_days` / `refresh_token_ttl` 存而不接**：当前管线无 refresh 流程，两字段仅存储与校验，接线随 refresh 模块（登记 §11.3-①）。
7. **密码策略**：`pwd_min_length/min_classes/forbid_username` 进创建/重置/自助改密三条新写入路径（存量不追溯）；`pwd_force_first_change=1` 时管理员代建/重置后置位 `sys_user.pwd_force_change`，登录响应 `pwd_must_change=true`，自助改密成功清除（`UpdatePassword` 不清标记——透明升级不算改密）；`pwd_max_age_days`/`pwd_remind_days`/`pwd_expire_action` 计算出登录/Me 响应三态：`password_stale`（兼容字段，语义=已过期）/`pwd_expiring`/`pwd_must_change`；`pwd_history_count` 配合 `sys_password_history`（改密前写旧 hash，新密码逐条 bcrypt 比对最近 N 行）；`allow_self_change_pwd=0` → 自助改密 **30053**。
8. **自助改密端点（新增）**：`POST /api/v1/admin/auth/change-password`（body `{old_password,new_password}`，需登录态）。文档 v1.0 隐含该入口（§2.4/§7"自助改密接口"）但 sys_user 文档未定义——本次随 P1.5 改密链路落地；旧密码错误计入与登录相同的锁定阈值（不写登录日志），成功按 `kick_on_pwd_change` 决定全端秒踢。
9. **缓存失效实测**：PUT 成功后下一次登录/读取即取新值（内存+Redis 双删）。
10. **读取端按端固定投影**（v1.2 用户裁定，替代 v1.1 的 GET 列表/GET :type 详情；v1.3 收敛）：
    - `GET /login-configs-admin` 写死 `config_type=1`；响应只含**前端编辑页（LoginConfigView.vue）实际绑定的 23 个字段 + `version`**（乐观锁必需）——不含 id/scope_id/config_type/extras/updated_by/时间戳；行缺失按 §3.2 兜底默认值投影；
    - **不设租户读取端**（v1.3 用户裁定：管理后台不拉租户数据）；租户配置的读取随租户登录模块在 `/api/v1/tenant/*` 体系自行定义，管理端对 type=2 仅保留 PUT/reset；
    - **布尔字段 0/1 数字收发**（kick_on_pwd_change/pwd_forbid_username/pwd_force_first_change/allow_self_change_pwd）：与前端 `LoginConfig` 接口的 number 类型对齐；PUT 侧由 v1.1 的 `*bool` 改为 `*int8`（`oneof=0 1`，nil=不改）——**接口变更，前端 PUT 载荷直接透传表单数字即可**；
    - 原 GET 列表/详情/`-tenant` 三个路由均已撤销，未注册（前端旧调用走 404 兜底码；前端仓需同步：list()→GET -admin，detail(1)→GET -admin，detail(2) 无后端读取端——租户 tab 走本地默认值）；
    - **`GET /login-configs-admin` 匿名可读**（v1.4 用户裁定，加入白名单 PublicPaths）：登录页未登录时按 `login_mask` 渲染登录 tab（§2.1 前端动态渲染的配套读取端）；注意该投影对匿名调用方暴露全部 24 字段（含冻结阈值/限流参数）——如需收紧可后续拆"登录页专用最小投影（仅 login_mask）"，当前按全量投影开放。

### 11.3 偏差登记（相对 v1.0 原稿）

1. `refresh_token_ttl`/`remember_days` 存而不接——管线无 refresh 流程，字段校验生效（规则 4/5），运行时生效随 refresh 模块落地；
2. §2.4 等级 3 附加规则"不含 3 位以上连续/重复字符"在明细字段中**无对应列**——按"明细字段是唯一真相"原则运行时不表达；等级 3 的可运行部分 = 长度 12 + 类别 3 + 禁账号名；
3. §6 规则 7"以明细为准反推等级"的确定性规则定为：高=长度≥12∧类别≥3∧禁账号名；中=长度≥10∧类别≥2；否则低（原稿未给算法）；
4. 操作日志：`sys_oper_log` 模块未落地，暂走既有 `log.Audit` 结构化打点（action=`loginconfig.update`，diff 记 from/to），模块落地后迁移；
5. 管理接口权限：`system:login-config:write` 独立权限点待权限模块落地后挂载，当前与字典模块同策略（登录即可访问）；
6. §3.2 seed `refresh_token_ttl` 604800→86400（自洽性修正，见 §3.2 说明）；
7. 运维提示：内置超管种子密码含账号名"admin"，违反默认策略 `pwd_forbid_username=1`——存量不追溯可正常登录，但下次改密不可再设置含"admin"的密码。
