## 0. 一句话方案

**后台加一行语言配置 + 前端放一个语言包文件 → 这门语言就能用。**

语言集合的真相从 `pkg/i18n/locales/` 目录搬到 `sys_lang` 表；语言包只负责"这门语言长什么样"，不负责"这门语言存不存在"。

## 1. 现状：语言集合被写死在四处

| 位置 | 内容 | 加一门语言要做什么 |
|---|---|---|
| `pkg/i18n/locales/*.json` | 后端错误码/提示文案包 | 加 JSON 文件 + **重新编译发版** |
| `pkg/i18n.Languages()` | 语言集合（扫目录得出） | 同上 |
| `domain/i18n/bit.go` `langBits` | 语言 → 掩码位 | **改 Go 代码** + 发版 |
| 前端 `locales/index.ts` | 6 个 `import` + `localeOptions` | **改 TS 代码** + 发版 |

四处不同步就是四类故障，而且都不报错、只在运行时露头：

- 后端有包、前端没包 → 下拉能选，界面满屏 key；
- 位没分配 → 该语言录入被 30035 拒，运营以为系统坏了；
- 前端有包、后端没启 → 翻了一半才发现下游不认；
- `localeOptions` 与后端 `Languages()` 顺序/数量不一致 → 切语言报"不支持"。

根因是同一件事：**"系统支持哪些语言"没有唯一真相，而是四份事实的巧合。**

## 2. 三个概念必须拆开

旧模型把三件事绑成一件（"已注册 = 可用"），所以加语言必须动代码。拆开后：

| 概念 | 含义 | 载体 | 变了要重算什么 |
|---|---|---|---|
| **注册** registered | 这门语言在系统里有身份（编码、掩码位、显示名） | `sys_lang` 一行 | 分配位 |
| **启用** enabled | 前端下拉可见、可录入译文、计入缺译统计 | `sys_lang.enabled` | `complete` 全表重算 |
| **默认** default | 唯一兜底语言；主表列存它的值 | `sys_lang.is_default` | `complete` 全表重算 + 前端 fallback |

状态组合与含义：

| 注册 | 启用 | 前端下拉 | 可录入译文 | 计入缺译 | 典型场景 |
|---|---|---|---|---|---|
| ✅ | ✅ | 显示 | 是 | 是 | 中文、英文（默认两款） |
| ✅ | ❌ | 不显示 | 否（30035） | 否 | 繁中/日/韩/西：包已就绪，等运营开 |
| ✅ | ✅ | 显示但置灰并提示"需发版" | 是 | 是 | 后台先开、前端包还没上（过渡态） |
| ❌ | — | — | 否 | — | 未注册语言，任何入口都不认 |

**关键判断：语言包的有无不再决定语言的存亡。** 前端没包时，这门语言只是"没翻译"，不是"不存在"——录入照样能进库，等前端发版即可显示。这条让"后台先配、前端后补"成为合法顺序。

## 3. 数据模型

### 3.1 DDL

```sql
CREATE TABLE IF NOT EXISTS sys_lang (
    id          BIGINT       NOT NULL COMMENT '雪花ID',
    lang_code   VARCHAR(16)  NOT NULL COMMENT 'BCP-47 标签，规范大小写：zh-CN / en-US / ja-JP；同时是前端语言包文件名',
    name        VARCHAR(32)  NOT NULL COMMENT '英文名：Chinese (Simplified)',
    native_name VARCHAR(32)  NOT NULL COMMENT '自称：简体中文 / English / 日本語',
    bit_index   TINYINT      NOT NULL COMMENT 'lang_mask 位序 0~62；落库后不可修改',
    is_default  TINYINT(1)   NOT NULL DEFAULT 0 COMMENT '默认语言，全表恰好一行',
    enabled     TINYINT(1)   NOT NULL DEFAULT 0 COMMENT '是否启用（前端下拉可见）',
    sort        SMALLINT     NOT NULL DEFAULT 0 COMMENT '下拉排序，小的在前',
    remark      VARCHAR(255) NOT NULL DEFAULT '' COMMENT '备注：谁在什么时候开的',
    created_at  DATETIME(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
    updated_at  DATETIME(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),
    PRIMARY KEY (id),
    UNIQUE KEY uk_lang_code (lang_code),
    KEY idx_lang_bit (bit_index),
    KEY idx_lang_pick (enabled, sort)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4 COLLATE = utf8mb4_0900_ai_ci;
```

**唯一键只留 `uk_lang_code` 一个。** 另外两条约束（位唯一、默认唯一）不建索引，改成"写路径固定 + 启动自检"：

| 约束 | 怎么保证 | 为什么不建唯一键 |
|---|---|---|
| 一门语言一行 | `uk_lang_code`，编码归一化后比较（`en_us` / `EN-US` 视为同一门），入库写规范大小写 | 它是运营手填的内容，**只有这条真的需要 DB 兜底** |
| 位不撞车 | 分配函数在**同一事务**里锁一行：`SELECT id, bit_index FROM sys_lang ORDER BY bit_index DESC LIMIT 1 FOR UPDATE` → `+1` → `INSERT`，行锁到提交才释放 | 位是服务端分配的派生值，运营看不到也不会填；建唯一键只是把并发撞车从一个状态码换成另一个错误，没解决问题 |
| 默认全表恰好一行 | 切换默认只允许一条原子语句：`UPDATE sys_lang SET is_default = (lang_code = ?)`，一条语句把全表置 0、目标置 1 | 生成列 + 唯一索引为一句"其实一条语句就能保证"的规则多养了一列一索引；真正的风险是有人写成单行 `SET is_default=1`，那是纪律问题，索引拦不住 |

两条纪律（写进代码注释，review 当硬性项看）：

1. `bit_index` **只能**由分配函数写入——任何接口、任何维护脚本都不许手填；
2. 默认语言**只能**用上面那条单语句切换——禁止 `SET is_default = 1 WHERE lang_code = ?`。

两条启动自检（整表 < 100 行，成本为零）：

```sql
SELECT COUNT(*) FROM sys_lang WHERE is_default = 1;                          -- 必须 = 1
SELECT bit_index, COUNT(*) c FROM sys_lang GROUP BY bit_index HAVING c > 1;  -- 必须空集
```

任一不满足 → 启动期 `ERROR` 日志 + 管理页红条，**但不阻断启动**（语言表异常不该把登录一起锁死，见 §8 兜底）。这比"等 INSERT 撞唯一键 500"更好定位：自检直接告诉你哪一位重复了。

### 3.2 初始化数据（幂等 seed）

固定 ID 段 `93` 开头，`INSERT IGNORE`：

```sql
INSERT IGNORE INTO sys_lang
    (id, lang_code, name, native_name, bit_index, is_default, enabled, sort, remark)
VALUES
    (930000000000000001, 'zh-CN', 'Chinese (Simplified)',  '简体中文', 0, 1, 1, 10, '内置默认语言，不可停用'),
    (930000000000000002, 'en-US', 'English',               'English',  2, 0, 1, 20, '内置第二语言'),
    (930000000000000003, 'zh-TW', 'Chinese (Traditional)', '繁體中文', 1, 0, 0, 30, '包已就绪，默认停用'),
    (930000000000000004, 'ja-JP', 'Japanese',              '日本語',   3, 0, 0, 40, ''),
    (930000000000000005, 'ko-KR', 'Korean',                '한국어',   4, 0, 0, 50, ''),
    (930000000000000006, 'es-ES', 'Spanish',               'Español',  5, 0, 0, 60, '');
```

位序 0/1/2 刻意与 `domain/i18n/bit.go` 现有 `langBits` **完全一致**（zh-CN=1、zh-TW=2、en-US=4）。存量 `lang_mask` 不改一个字节，seed 只是把常量搬进表。

**默认只启用 zh-CN + en-US**：另外四门包已在仓库里，运营一键开启即可，不需要发版。

### 3.3 为什么不是 `sys_config` 的 key-value

语言是**实体**：有位、有顺序、有启停、有唯一性约束、会被引用（`lang_mask` 位、用户偏好）。塞进 `sys_config`（key-value 字符串）意味着位表、排序、唯一默认全靠字符串解析 + 应用层校验，一并发就出错。实体就该建表。

### 3.4 为什么不用字典（`sys_dict`）

「系统里已经有一套字典了，为什么语言不塞进 `dict_type='lang'`？」——这是本节要回答的问题，因为它看起来省一张表，实际上会把三个**数据库级硬约束**降级成应用层约定。

#### 3.4.1 字典能提供的，和语言需要的

| 维度 | 语言需要 | 字典（`sys_dict_item`）能给什么 |
|---|---|---|
| 位序 | `bit_index` 唯一、不可改 | **没有这个列**；塞 `remark`/ext JSON = 位从"强类型列"退化成"字符串解析" |
| 位唯一 | 专用分配函数（同一事务行锁串行）+ 启动自检 | 没有位概念；塞进 ext JSON 也只能靠人填，没有分配函数、没有串行化，也没有自检对象 |
| 删除语义 | **禁止删除**，停用即墓碑，位永不释放 | 软删（`deleted_at` 参与唯一键）→ 允许删后重建同 `value` 的**新行**，新行没有旧位，历史 `lang_mask` 无法解释 |
| 默认唯一 | 一条语句原子切换 + 启动自检 | 只有一个 `status`，没有"组内恰好一行"的表达力，也没有"一条语句改全组"的写路径 |
| 行含义 | 语言 = 系统结构参数（决定 `complete` 口径） | 字典项 = 业务枚举值（决定"下拉里有哪几项"） |

前四条不是"实现起来麻烦"，是**约束强度差一个量级**：语言表有位分配函数、默认切换单语句、禁删墓碑这三条硬写路径，字典表连**表达这些概念的位置**都没有（它只有 `value` / `status` / `sort`）。

#### 3.4.2 更硬的一条：循环依赖

字典项的 `label` 本身是可翻译资源（`res_type='dict_item'`，存 `sys_i18n_text`）。如果语言集合也放在字典里：

```
要读"有哪些语言"        → 查字典项
要正确显示这些语言的名字  → 按当前语言翻译字典项 label
要翻译                     → 需要知道"当前语言"是否合法
"当前语言"是否合法         → 回到第 1 步：查字典项
```

这不是理论问题：语言下拉要在**登录页、未认证状态**下就能用，而字典接口默认要求登录态，且类型停用会连带项不下发（字典 §30047）。一旦 `lang` 类型被误停用，`langs` 接口返回错误 → 翻译坐标系消失 → 连"报错信息该用哪种语言"都答不出来。

**结论：语言列表是"翻译的坐标系"，它不能依赖翻译系统本身。** 所以 `sys_lang` 的显示名用 `native_name`（母语自书：简体中文 / English / 日本語）——语言选择器按惯例就该用母语名显示，**不需要翻译，也不进 `sys_i18n_text`**。这一条同时省掉了循环，也省掉了"翻译页里出现语言名字"的荒谬页签。

#### 3.4.3 生命周期、权限、生效面都不同

| | `sys_lang` | 塞进字典 |
|---|---|---|
| 变更频率 | 季度级，6~10 行 | 字典是日常增删的业务枚举 |
| 变更后果 | 触发 `complete` 全表重算、要求前端发版配合 | 字典是普通 CRUD，没有任何重算钩子 |
| 权限 | 独立权限点 `system:lang:write`（等同改系统能力） | 复用字典权限，粒度表达不了"高危" |
| 审计 | 必须记 diff（谁把语言集合改了） | 字典审计不区分"改了个业务枚举"和"改了系统能力" |

#### 3.4.4 如果硬塞进字典，会以什么方式出事故

1. **位漂移**：运营删掉 `ja-JP` 项又重新建了一个 → 新项没位（或复用了旧位）→ 历史行 `lang_mask` 里那一位要么变成孤儿、要么把日文译文算成韩文。
2. **并发抢位**：两个管理员同时开 `ja-JP`、`ko-KR`，应用层"查最大位 +1"都读到 5 → 两行都是 6 → `complete` 从此永久算错，且**不报错**。（现在由 §4 纪律 3 的事务行锁封住；但这也说明：一旦有人绕开分配函数手填位，**没有任何索引会拦你**——只有启动自检会在下次重启时喊出来。）
3. **级联失联**：字典类型被停用（本来只是"这个枚举先别下发"）→ 语言列表整块消失 → 前端回退默认语言、译文管理页打不开语言下拉，故障面远超"停用一个枚举"。

#### 3.4.5 判据：什么进字典，什么进独立表

> **这个集合是否被代码当作"结构参数"——有位、有唯一约束、会决定其他表的数据完整性口径？**

- 是 → 独立表（`sys_lang`）。判据的具体表现：它出现在 `lang_mask` 这种位运算里、它决定 `complete` 的定义、它被 `uk` 约束保护。
- 否 → 字典（`sys_dict`）。导入类型、文件状态、员工类型、合同类型——纯展示、纯选择、可随意增删、删了不影响别人的数据完整性。

语言属于前者。**UI 可以复用（语言管理页照样用字典那种列表 + 启停 + 排序的交互），存储不能复用**——这是两件事。

## 4. 位掩码：配置化之后如何不破坏存量数据

`lang_mask` / `complete` 的语义一个字不改（见 i18n 文档 §2.4）：**mask 记录"这行有哪些语言的译文"，complete = mask 是否覆盖"当前启用的全部非默认语言位"**。变化只在"位从哪里来"。

四条纪律：

1. **位只追加，严禁重排。** 位序一旦落库即成事实，在中间插一门语言会让全部历史行的位含义整体错位——那不是 bug，是数据损坏（把日文当成韩文）。
2. **位落库后不可修改。** `bit_index` 不进任何更新接口；要"换位"只能新建一门语言。
3. **分配算法 = 当前最大位 + 1，且必须锁行取**：
   ```sql
   BEGIN;
   SELECT id, bit_index FROM sys_lang ORDER BY bit_index DESC LIMIT 1 FOR UPDATE;  -- 锁住末位那一行
   -- 应用层 +1（空表从 0 起；0/1/2 为已用位）
   INSERT INTO sys_lang (..., bit_index, ...) VALUES (..., ? , ...);
   COMMIT;
   ```
   行锁到提交才释放，并发新增自然串行。**没有 `uk_lang_bit` 可冲突，所以不存在"冲突重试"这条路**——省下的索引，代价是这条路径不能绕过。可用位 **0~62，共 63 门**（`BIGINT` 符号位不用）。
4. **停用不释放位（墓碑语义）。** 停用后该位仍被历史行占用；重新启用时旧译文原样复活。位耗尽时报 30042，**绝不回收复用**——复用等于把别人的译文认成自己的。

位耗尽的处理：语言管理页直接禁用"新增"按钮并提示"位已用尽（上限 63 门）"，而不是等保存失败才报错。

### 4.1 兼容迁移

| 步骤 | 内容 |
|---|---|
| 1 | 建表 + §3.2 seed（`INSERT IGNORE`，可重复执行） |
| 2 | `domain/i18n/bit.go` 的 `langBits` **保留**，但降级为"迁移来源 + 单测守卫"：`TestLangBitsCoverSeededLangs` 断言 seed 的 code/位 与常量表一致，防两边漂移 |
| 3 | `FullMask` / `LangBit` 的数据源从静态 map 改为运行时注册表（§8），签名不变，调用方零改动 |
| 4 | 前端不动：6 个包继续打包，下拉改由接口驱动，自然只剩 2 项 |

第 2 步的静态表是刻意留的：它是"位序不许变"这条纪律在编译期的锚，删了之后没人能挡住下一个人重排。

## 5. 启用 / 停用的连锁反应

这是最容易漏的部分——**语言开关不是纯展示开关，它改变"完整"的定义**。

| 动作 | 必做 | 说明 |
|---|---|---|
| 启用某语言 | `complete` 全表重算 | 全集变大，原本"完整"的行可能变缺译 |
| 停用某语言 | `complete` 全表重算 | 全集变小，缺译清单里该语言的行消失 |
| 切换默认语言 | `complete` 全表重算 + 旧默认语言位处理 | 默认语言不进译文表，其位恒 0（i18n §2.4） |

重算就一条 SQL（按注册表算出新全集 `$full`）：

```sql
UPDATE sys_i18n_text
SET complete = IF((lang_mask & $full) = $full, 1, 0)
WHERE deleted_at = 0;
```

执行方式：**异步任务 + 幂等**。触发点三个——语言配置保存后、服务启动自检（比对 `sys_lang` 版本与上次重算版本）、手动"重算"按钮。任务带 `registry_version`，重复执行结果一致。

三条业务规则：

1. **默认语言不可停用、不可删除**：先切默认，再停旧默认。服务端拒绝（30043），前端把开关置灰并给提示。
2. **停用后用户偏好回退默认**：用户偏好存的是 `lang_code` 字符串，读取时校验是否在启用集合内，不在则回退默认语言（不是报错）。
3. **启用语言后缺译数暴涨是正确行为**：不要为了数字好看去隐藏缺译行。管理页在启用前提示"将新增 N 条缺译（估算 = 已有译文行数）"，让管理员有预期。

## 6. 前端契约（判定规则 + 后端接口约束）

前端已按"**语言包 `.ts` + 下拉由接口驱动**"落地，本文**不给前端实现代码、不列前端文件清单**。本节只写两件事：后端必须稳定提供什么（少给一个字段会坏在哪）、以及**"后台启用了但前端没包"这一条必须由前端判定并兜住**（后端无从判断）。

### 6.1 前端现状（背景，不是待办）

- 语言包 = `src/locales/{lang_code}.ts`，编译期打包；**文件名即语言编码**，`zh-CN.ts` 的 key 结构即其他包的 `LocaleSchema`，缺 key 编译期就红——语言包不会"半套"上线。
- 语言包只在编译期参与，**后端感知不到"前端有没有包"**。所以"后台启用了但前端没包"只能由前端发现（§6.3）。
- 新增语言 = 加一个 `.ts` 包 + 发布，不改装配代码、不动本文任何后端设计。

### 6.2 后端必须保证的返回（`GET /api/v1/i18n/langs`）

| 字段 | 用途 | 缺了会怎样 |
|---|---|---|
| `code` | 与前端包文件名匹配（`zh-CN` ↔ `zh-CN.ts`，忽略扩展名与大小写） | 下拉项全部置灰，等于语言不可选 |
| `nativeName` | 下拉显示。**语言用母语自书，不做翻译**（§3.4.2） | 下拉显示成编码 |
| `isDefault` | 前端 `fallbackLocale` 的锚点 | 回退到写死的 zh-CN，与后台默认语言脱钩 |
| `sort` | 下拉顺序 | 顺序抖动 |
| `defaultLang`（顶层） | 与 `isDefault` 冗余，便于前端一次取值 | 同 `isDefault` |
| `version`（顶层） | 前端缓存键 / `ETag` | 前端只能靠时间过期，配置改了要等 |

**不下发 `packFile`**：前端包文件名恒等于 `lang_code`（`zh-CN.ts`），多一个字段只会多一种"后端说 A、前端文件叫 B"的错法。真要支持别名，先把命名规范改掉，别加字段。

三条硬约束：

1. **必须公开可访问**（免登录）：登录页的语言下拉就在这个接口上，要求登录态等于死锁。
2. **只返回 `enabled=1`**：停用语言不能出现在公开接口里，前端不做二次过滤（前端过滤只是兜底）。
3. **失败也必须能返回**：DB 不可用 / `sys_lang` 为空时返回内置 `zh-CN` + `en-US`（§8），**绝不 500**——语言接口 500 会让登录页白屏。

### 6.3 包存在性判定：前端是唯一裁判

后端只能告诉你"这门语言已被后台启用"，**永远无法知道用户当前加载的这版前端有没有它的语言包**。所以"启用了一门前端没包的语言"这个坑，只能由前端自己发现、自己兜住——而且**不是下拉框里一个灰项就够**：判定要落在四个时刻（§6.3.1），靠三条硬不变量兜底（§6.3.3 B）。

#### 6.3.1 判定时机（少一个就会漏）

| 时刻 | 漏了会怎样 |
|---|---|
| **启动装配后、挂载前** | `localStorage` 或上次会话可能存着无包语言 → 首屏全站文案变 key 原文 |
| **`GET /i18n/langs` 返回后** | 后台新启用的语言首次出现在 `items` 里 → **这是"启用后前端自己判断出来"的主战场** |
| **用户点下拉 / 带 `?lang=` / 恢复偏好** | 灰项只置灰不禁用，脚本或手快仍能选中 |
| **`version` 变化（配置热更新、长驻标签页）** | 会话期间后台停用了某语言或新启用了无包语言，当前 locale 已非法却无人复核 |

#### 6.3.2 判定算法

```
hasPack(code) =
     packs[normalize(code)] != null
  || packs[normalize(code).split('-')[0]] != null     // 主标签兜底：ja 可服务 ja-JP

normalize(s) = s.trim().toLowerCase().replace(/_/g, '-').replace(/\.(ts|js|json)$/, '')
```

三条归一化必须一致执行：**忽略扩展名**（包文件是 `{code}.ts`，去掉扩展名就是 code 本身）、**忽略大小写**（`zh-tw` ↔ `zh-TW`）、**`_` 视同 `-`**。主标签兜底是给"只做了 `ja.ts`、没做区分子标签"的包留的活口：命中即认为有包；请求头仍发 `ja-JP`，不影响后端取数。

#### 6.3.3 判定结果的处置

**A. 运营点"启用"的那一刻——最该被拦住的地方**

前端此刻手里同时有 `packCodes` 和待启用语言，弹二次确认，把后果写成人话：

| 判定 | 弹窗 |
|---|---|
| 有包 | 正常启用，不打扰 |
| 无包 | **警示型确认**："当前前端版本未包含 ja-JP 语言包。启用后下拉会出现「日本語」但置灰不可选，界面文案无法显示为日文；需前端发版后自动可用。是否继续？" → 确认后才发请求 |

继续启用是允许的：后台配置和前端发布是两条流水线，不该互相锁死。但操作者必须当场知道后果，而不是等用户报障。

> 可选（建议做，成本一行）：启用请求带 `ackNoPack: true`，后端写进操作日志 `detail`——事后能查清"当时是否明知无包仍然启用"。**不要**把它存成表字段当判定依据，它只是一次操作的审计快照，换台机器就不成立。

**B. 运行期：三条硬不变量（不依赖运营有没有点确认）**

1. **`activeLocale` 必须命中 pack**。偏好/URL/浏览器语言指向无包语言时 → 强制切到 `defaultLang`（有包才用）→ 再不行用内置 `zh-CN`。**绝不 `setLocale` 到无包 code**，否则全站文案变 key。
2. **`fallbackLocale` 也必须命中 pack**。vue-i18n 的 fallback 指向无包语言时，缺失 key 照样吐 key 原文，回退链等于断了。所以前端实际算三档：`active → defaultLang（有包才用）→ zh-CN（内置必在）`。
3. **下拉项 `disabled`，不只是灰**。灰是视觉，`disabled` 才是行为；提交前再校验一次，防 `?lang=ja-JP` 这类绕过。

**C. 把"判断出来"变成可见信号（否则等于没判断）**

- 管理端顶部 banner（仅管理员可见、可关闭、按 `version` 去重）：**"后台已启用 N 门语言，当前前端版本缺少语言包：ja-JP、ko-KR。这些语言在下拉中置灰，需前端发版后生效。"**
- 控制台 `warn` 输出同一份清单，便于一线排障一眼看到。
- 仍然**不隐藏**置灰项：隐藏会让运营以为配置没生效，反复改配置（原结论保留）。

#### 6.3.4 检测不到的部分（写清楚，别假装能兜）

| 情况 | 为什么检测不到 | 兜底 |
|---|---|---|
| 有包但内容是中文占位/机翻 | 文件存在即"有包"，内容质量无法程序化判定 | 靠 review + 上线前抽样；CI 只比 key 集合，不做语义检查 |
| **`isDefault` 指向无包语言** | 前端能发现，但这是配置事故 | 前端降级到 `zh-CN` 包 + banner 红字置顶；后端切默认语言时无法校验包，只能靠这一层报出来 |
| 语言包被误删（后台仍启用） | 前端只看到"无包"，看不到"曾经有" | 规范：**删包前必须确认后台该语言已停用**；孤儿包（有包未启用）不删，几 KB 而已 |

### 6.4 回退链

| 层 | 回退顺序 | 归谁管 |
|---|---|---|
| 界面文案（语言包） | 当前语言（无包则跳过）→ 默认语言（无包则跳过）→ 内置 `zh-CN` → key 原文 | 前端 |
| 数据文案（DB） | 请求语言 → 默认语言主表值 → `''` | 后端（i18n §4） |
| 后端错误文案 | 请求语言包 → 默认语言包 → `"500"` | 后端（`pkg/i18n`） |

三层回退都锚在同一处：`sys_lang.is_default`。**切换默认语言会同时改变三层的兜底结果**，这也是它必须走二次确认 + 重算的原因（§5）。注意界面文案这一档比另两档多一次"包存在性"过滤——那是前端独有的信息。

### 6.5 语言切换

前端切换语言只做三件事：改 `i18n.global.locale`、存 localStorage、后续请求带新 `Accept-Language`。后端按该 header 返回数据文案与错误文案——**不需要任何"切换语言"的接口**，语言偏好是浏览器侧状态，不落库（落库是"用户偏好语言"字段，另一个话题）。

前置条件：切换前必须过 §6.3.2 的 `hasPack`；`version` 变化后重新拉 `items` 并复核当前 locale，若已停用或无包 → 提示一次 + 回退，不静默重置。

### 6.6 语言怎么传：请求头 + 优先级链

**结论：全站默认 `Accept-Language`；导出/分享/打印类 URL 叠加 `?lang=`。** 前端现状已是这个方式（请求拦截器统一注入），本节把它固化成后端契约。

#### 6.6.1 为什么是 `Accept-Language` 而不是 `X-Lang`

| 维度 | 说明 |
|---|---|
| 无状态 | 切语言不重签 token、不踢下线、不清缓存、不广播；多实例部署无会话亲缘性 |
| 免预检 | `Accept-Language` 属 CORS safelisted header，跨域不触发 OPTIONS；自建 `X-Lang` 每次都多一跳 |
| 可观测 | 网关、Nginx、APM 天然认识，排查"这请求要哪门语言"不用翻代码 |
| 语义正确 | 本义即"可接受语言的偏好序列"，单值只是特例 |

#### 6.6.2 解析优先级（服务端唯一入口）

```
?lang=  >  Accept-Language  >  登录用户偏好(DB，仅无头时)  >  sys_lang.is_default
```

| 顺序 | 来源 | 为什么在这个位置 |
|---|---|---|
| 1 | `?lang=` | 显式覆盖：分享链接、导出、打印预览、iframe 嵌入、第三方对接。**只做覆盖、不做常态**——全站靠 query 会把日志与缓存 key 弄脏 |
| 2 | `Accept-Language` | 前端每请求声明本次偏好，跟浏览器/标签页走，多标签可不同语言 |
| 3 | 用户偏好（DB） | 只在无头时查（第三方调用、旧客户端）；**有头时以头为准**，避免"用户改了偏好但当前标签页仍是旧语言"的错位 |
| 4 | `is_default` | 兜底，与 §6.4 三层回退锚在同一处 |

解析规则（中间件一次做完，结果写进请求上下文）：取**第一段** → 忽略 `q=` → trim 后 ≤ 35 字符 → `_` 归一为 `-` → 大小写归一 → 查注册表 → **未注册或已停用则静默回落默认语言 + debug 日志，绝不 400**（一个过期的浏览器语言值不该让人登不进去）。

#### 6.6.3 两个响应头（不做就是线上事故）

| 头 | 值 | 不做会怎样 |
|---|---|---|
| `Vary` | `Accept-Language` | 前面只要有 Nginx/CDN/浏览器缓存，同 URL 会按首个请求的语言被缓存 → 英文用户拿到中文响应；**往往只在第二个人访问时复现**，极难查 |
| `Content-Language` | 实际解析出的语言 | 排障对账无据；前端也无法发现"响应用的是旧语言"（§6.6.7） |

#### 6.6.4 写接口：语言维度必须在 body，不能在头

- 译文写入接口的 body 必须显式带语言维度（`{"zh-TW":"…","en-US":"…"}`），头**只决定错误提示用哪种语言返回**。
- 反例：若用头推断"这次改哪门语言"，管理员把界面切成英文再保存，就会把英文写进中文行——不可逆的数据污染。
- 同理：操作日志 `detail` 里记录文案时也要带语言维度，不隐式继承请求头。

#### 6.6.5 异步任务：创建时快照语言

导出 Excel、生成报表、发邮件/短信模板：**创建任务时**把解析出的语言写进任务记录（`lang` 字段），worker 用快照值渲染。异步链路没有"当前请求"，靠 header 只能拿到 worker 的默认语言——用户选了日文却收到中文文件。

#### 6.6.6 头表达不了的场景

| 场景 | 做法 |
|---|---|
| 译文管理页（一次编辑全部语言） | 管理端接口**默认返回全量 `texts` map**，与头无关；头只影响外层提示文案 |
| 同页并排校对多语言 | 同上，一次取全量，不发多次不同头的请求 |
| C 端业务列表 | 按头返回单语言展示值；全量走管理端接口（i18n §7） |

#### 6.6.7 切换瞬间的在途请求

切语言前发出的请求仍会用旧语言返回，可能出现"新界面 + 旧数据文案"混排。处理二选一：切语言时 abort 未完成请求并重拉；或校验响应 `Content-Language` 与当前 locale 不一致则重拉一次。

#### 6.6.8 为什么不用别的

| 方案 | 优点 | 不作为默认的原因 |
|---|---|---|
| URL path 前缀 `/en/…` | SEO 友好、分享自带语言 | 要改路由与网关；后台管理不需要 SEO |
| `?lang=` 全站 | 天然进缓存 key、可分享 | 污染所有日志与统计；GET 语义被附加参数打乱；只适合导出/公开页 |
| Cookie | 自动携带、前端零代码 | 跨域/CSRF 处理麻烦；同浏览器多标签无法不同语言 |
| 自定义 `X-Lang` | 语义干净、不怕 q 值 | 跨域触发预检；网关/APM 不识别 |

## 7. 接口设计

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/v1/i18n/langs` | **公开**（免登录）：登录页语言下拉、启动引导；带 `ETag`/`Cache-Control: max-age=60` |
| GET | `/api/v1/admin/langs` | 管理列表：含停用语言、位序、使用量；需登录 |
| POST | `/api/v1/admin/langs` | 新增：`code`、`name`、`nativeName`、`sort`、`remark`；**位由服务端分配**，`enabled` 默认 false |
| PUT | `/api/v1/admin/langs/{code}` | 改名/排序/启停；**不含 `bit_index`**（传了忽略并告警）；启停触发 complete 重算 |
| PUT | `/api/v1/admin/langs/{code}/default` | 切换默认语言：二次确认 + 重算 + 审计 |
| GET | `/api/v1/admin/langs/{code}/usage` | 停用前的影响面：多少行有该语言译文、多少用户偏好该语言 |

约定：

1. **不提供物理删除。** 删除一行会让 `lang_mask` 里那一位变成"无主的位"，历史数据无法解释。要下线就停用（墓碑）。文案里明确写"停用"而不是"删除"，避免运营误解。
2. 新增语言时 `code` 校验：`^[a-z]{2,3}(-[A-Z]{2})?$`（BCP-47 简化版），归一化后查重（`en_us`、`EN-US`、`en-US` 都算重复，30044）。
3. 保存后：删缓存 → 写操作日志（diff）→ 异步重算 → 返回 `version`。
4. 权限点：`system:lang:write`。能改语言集合的人，等于能改"系统支持什么"，与登录策略同级。

错误码（`pkg/code` 五处同步）：

| 码 | 含义 |
|---|---|
| 30035（语义扩展） | 语言未注册或未启用（原"语言无位"） |
| 30042 | 语言位已耗尽（上限 63 门） |
| 30043 | 默认语言不可停用/删除 |
| 30044 | 语言编码已存在 |

### 7.1 菜单归属：放「基础工具」下（`/tools`）

**结论：多语言管理是工具，不是运维动作，归 `基础工具`。** 它做的是"内容/配置维护"，与"文件管理"同类；`系统运维` 放的是网站配置、登录配置、各类日志这类**系统级、高危、低频**动作，混进去会让运维菜单变成杂物间。

菜单结构（`sys_menu` 运行时配置，非 SQL seed）：

```
基础工具  /tools              type=1  目录   icon: Tools
├── 文件管理      /tools/files   type=2  sort=40  icon: FolderOpen
└── 多语言管理    /tools/i18n    type=2  sort=41  icon: Languages
        ├── tab 译文管理   ← sys_i18n_text（§6.6.6 全量 texts）
        └── tab 语言配置   ← sys_lang（本文 §2 三态：注册/启用/默认）
```

四点说明：

1. **一个菜单、两个 tab，不拆两个菜单**。两者是同一件事的两面：改语言集合会改"哪些语言需要译文"，改译文又需要知道有哪些语言；拆开会让"启用语言后去录译文"变成跨菜单来回跳。权限点仍在接口层分开（`system:lang:write` / `i18n:text:write`），页面级只要求一个查看权限。
2. `sort=41` 紧跟文件管理（40），保持"工具类"聚在一起；后续新增工具从 42 往后接。
3. **前端现状已与此一致**：路由 `/tools/i18n`、分组 `menu.tools` 已就位，只差把标题从"译文管理"改为"多语言管理"、页面内加"语言配置"tab。**不改路径**——`/tools/i18n` 已是既成事实，改名会破坏书签与外链，收益为零。
4. 若后续语言配置膨胀（多租户覆盖、语言包托管、翻译工作流），再拆成子菜单 `/tools/i18n/langs`、`/tools/i18n/texts`；**现在不拆**，两个 tab 足够。

配套两条：

- 权限点：页面查看 `system:i18n:list`（或沿用登录态即可，见 i18n §7 的"权限未生效"诚实说明）；写入分别 `system:lang:write`、`i18n:text:write`。
- 繁体菜单基线：新增节点后需在 `application/menus/backfill.go` 的 `traditionalNames` 登记 `{path: "/tools/i18n", TW: "多語言管理"}`，否则繁中界面回退简体（见《菜单繁体中文存量数据补齐建议》§6 末段）。

## 8. 运行时注册表与缓存

```
启动/首次访问 → 加载 sys_lang（全表 < 100 行）
             → 构建 Registry{Langs, ByCode, BitOf, FullMask, Default}
             → atomic.Value 持有，读零锁
```

- **刷新**：写操作后主动 reload；另有 30s 兜底轮询（防多实例部署时别的节点改了配置）。
- **兜底**：加载失败或表为空 → 内置 `zh-CN` + `en-US` 两门语言的硬编码 registry，并告警。**绝不因为读不到语言表就拒绝登录**——否则一次 DB 抖动能把整个后台锁在门外。
- **版本号**：`version = MAX(updated_at) 的毫秒时间戳字符串`，用于前端 ETag 与重算任务的幂等键。
- 不用 Redis：数据量极小、变更极少，多一跳网络只增加不一致窗口。

## 9. 新增一门语言的完整 SOP（也是验收脚本）

以日语为例，五步：

| # | 谁做 | 做什么 | 是否要发版 |
|---|---|---|---|
| 1 | 开发 | 后端 `pkg/i18n/locales/ja-JP.json`（错误码文案；缺了也能跑，回退默认语言） | 后端发版 |
| 2 | 前端 | 加语言包 `src/locales/ja-JP.ts`（复制默认包改名补翻译；机制已实现，**不改任何代码逻辑**） | 前端发版（唯一硬性一步） |
| 3 | 运营 | 后台「语言管理」→ 新增 `ja-JP`（位自动分配=6）→ 启用（若第 2 步还没发版，前端此时会弹"当前版本无该语言包"确认，属预期） | 否 |
| 4 | 运营 | 译文管理逐条录入 / 批量导入；缺译清单核对 | 否 |
| 5 | 运营 | 用户下拉出现「日本語」，切换后菜单/字典/界面全部日文 | 否 |

**验收标准**：第 3~5 步全程不写一行 Go / Vue 代码、不发版；第 1~2 步是"加语言包"，正是用户诉求里的"前端加个语言包"。停用后再启用，旧译文必须原样回来。

## 10. 零发版方案（评估后一期不做）

真正"后台配一下、前端立刻有"需要语言包不走编译期：

- 语言包 JSON 由后端托管（静态目录 / OSS），前端启动 `fetch` 后 `setLocaleMessage`；
- 与现有的 `.ts` 包**并存不冲突**：`.ts` 是编译期基线，远程包按 `{lang_code}.json` 命名并覆盖同名 code 的 messages（远程优先、失败回退基线）；
- 代价：首屏多一次阻塞请求（或接受一次闪烁）、版本一致性与缓存策略、加载失败要降级到内置包、语言包体积不受 tree-shaking 控制、**丢了 `.ts` 的编译期 key 校验**；
- 收益：新增语言零发版。

**结论**：一期不做。管理后台的语言变更频率是"季度级"，为它引入运行时资源加载，复杂度换来的收益不成立。等真的出现"客户要求每周加一门语言"，再按 `{lang_code}.json` 的命名约定接远程包——命名即协议，**不需要给表加任何字段**。

## 11. 边界情况清单

| 情况 | 处理 |
|---|---|
| `sys_lang` 表空 / 加载失败 | 内置 zh-CN+en-US 兜底 + 告警，登录不受影响 |
| 位耗尽（63 门） | 新增接口拒绝 30042；管理页禁用新增按钮并提示 |
| 并发新增两门语言抢同一位 | 分配函数在同一事务内 `SELECT … FOR UPDATE` 锁末位行 → 串行分配；无唯一键可冲突，也就没有"重试"逻辑 |
| 有人绕过接口手写 `bit_index` / 单行 `SET is_default=1` | 违反 §3.1 两条纪律；启动自检（默认数=1、位无重复）会报 ERROR + 管理页红条 |
| 新增 `en_us` 而库里已有 `en-US` | 归一化查重 → 30044 |
| 停用默认语言 | 拒绝 30043，提示先切换默认 |
| 停用某语言时已有用户偏好该语言 | 允许停用；该用户下次请求回退默认语言 |
| 后台启用、前端无包 | **前端判定**（§6.3）：启用时二次确认 → 下拉置灰且 `disabled` + 管理端 banner 列出无包语言 + console.warn；不隐藏（隐藏会让运营以为配置没生效） |
| 偏好/URL 指向无包语言 | 启动即判定 → 强制回退 `defaultLang`（有包才用）→ `zh-CN`；**绝不 setLocale 到无包 code** |
| `isDefault` 指向无包语言 | 前端降级到 `zh-CN` 包 + banner 红字置顶；属配置事故，需人工改回 |
| 会话中后台启用无包语言（`version` 变） | 重拉 `items` 后复核：当前 locale 仍合法则不动，下拉新增置灰项，banner 出现 |
| 请求头语言未注册/已停用/格式非法 | 静默回落默认语言 + debug 日志，**不 400**；解析规则见 §6.6.2 |
| 响应漏了 `Vary: Accept-Language` | 缓存层按首个请求语言串页（第二个访问者才暴露）；中间件统一加，并回 `Content-Language` |
| 异步导出/邮件跨语言 | 任务创建时快照 `lang`，worker 读快照、不读请求头（§6.6.5） |
| 切语言瞬间的在途请求 | 响应 `Content-Language` 与当前 locale 不一致 → abort 重拉（§6.6.7） |
| 语言包缺 key | **编译期**：`.ts` 包按 `LocaleSchema` 检查，缺 key 直接 `tsc` 报错；**运行期**兜底：回退默认语言包 → key 原文，dev 期 warn，生产不弹错 |
| 启用语言后缺译数暴涨 | 正确行为；启用前弹提示告知预估条数 |
| 切换默认语言 | 二次确认 + 全表重算 + 不自动改写存量主表值（i18n §4 规则 4） |
| 多实例部署，A 节点改了配置 | 30s 轮询兜底；写操作后本节点立即 reload |
| 存量 zh-TW 数据在停用状态下 | 位保留，`complete` 不计该位；启用后重算即恢复口径 |
| 前端 localStorage 存了已停用语言 | 启动校验失败 → 回退默认语言，静默改写存储 |

## 12. 实施顺序

**全部为后端工作**——前端已实现语言包与下拉，不在本节范围内。

| 阶段 | 内容 |
|---|---|
| **P0** | 建表 + seed + 迁移；registry（加载/缓存/兜底）；`Meta`、`FullMask`、`LangBit` 换源；`GET /i18n/langs` 上线；请求级语言解析中间件（§6.6.2 优先级链 + `Vary` / `Content-Language`） |
| **P1** | 语言管理接口（列表/新增/启停/切默认）+ 校验 + 权限点 `system:lang:write` + 操作日志 diff；管理页前端由前端侧排期，不在本文 |
| **P1.5** | `complete` 重算任务（含启动自检与手动按钮）；`usage` 影响面接口；`registry_version` |
| **P2** | 远程语言包（§10，JSON 运行时覆盖 `.ts` 基线）——**需前端配合**，后端只负责托管 `{lang_code}.json` 静态资源 |

P0 验收：**库里只启用 zh-CN/en-US 时，前端下拉只有两项；把 ja-JP 的 `enabled` 改 1，下拉立刻多出「日本語」（前端已含包）**——链路就是活的，且这一条只用后端改动就能验证。
