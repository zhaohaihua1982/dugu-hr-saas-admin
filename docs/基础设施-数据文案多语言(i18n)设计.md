## 0. 先划一条线：代码文案 vs 数据文案

多语言在这个系统里有两个完全不同的层，混在一起是绝大多数"多语言做成半吊子"的根因：

| | **代码文案** | **数据文案**（本文范围） |
|---|---|---|
| 例子 | 按钮"保存"、校验提示、错误码 30041 的 msg | 菜单名"用户管理"、字典项"员工花名册"、将来的部门名 / 岗位名 / 公告标题 |
| 谁维护 | 开发 | 运营 |
| 存哪 | 前端 `src/locales/*.ts`；后端 `pkg/i18n/locales/*.json` | **数据库**（本文的 `sys_i18n_text`） |
| 加一门语言的代价 | 改代码 + 发版 | 插行数据，即时生效 |
| 数量级 | 几百条，随功能增长 | 几千~几万条，随运营增长 |

**判据一句话：这份文案改了要不要发版？** 要 → 代码文案，进语言包；不要 → 数据文案，进这张表。

**最常见的误用**：把按钮文案塞进 DB。后果是改一个错别字要找运营、要走后台、还可能与已发布的前端版本不同步。反过来，把菜单名硬编码进前端语言包，运营连改个错字都得提需求——这两个方向的错都真实发生过。

## 1. 核心决策：一张通用翻译表，而不是每个资源一张子表

### 1.1 三个方案

| 方案 | 新增一个可翻译资源的成本 | 约束强度 | 机制一致性 | 判定 |
|---|---|---|---|---|
| 主表加 `name_en` / `name_ja` 多列 | 改表 + 改 PO/DTO/前端映射 | 强 | 差（列数随语言线性增长） | ❌ |
| **每个资源一张子表**（现状：`sys_menu_i18n`、`sys_dict_item_i18n`） | 建表 + 建 DAO + 写一遍 fallback + 前端再来一遍 | 强 | **靠人守，必然漂移** | ⚠️ 仅当资源只有 1~2 个 |
| **通用表** `sys_i18n_text` | 在 domain 注册一个常量 | 中（靠白名单 + 校验） | **机制唯一，不可能漂移** | ✅ 采用 |

### 1.2 为什么选通用表

本项目要翻的东西有个共同特征：**资源很多，每个只翻 1~2 个字段**。

- 菜单：40×3 行，字段只有 `name`
- 字典项：100×3 行，字段只有 `label`
- 将来：部门 `name`、岗位 `name`、公告 `title` + `content`、租户自定义字段的 `label`……

按"每资源一张子表"做，会得到 N 张字段几乎完全相同的表（`id, xxx_id, lang, 文案, deleted_at, created_at, updated_at`）+ N 份几乎相同的 DAO + N 处各自实现的 fallback。**这才是真正的重复**，而且一致性只能靠规范约束，实际项目里第三张表开始就必然写歪（漏兜底、漏归一化、漏软删）。

### 1.3 通用表的代价，以及对策

| 代价 | 对策 |
|---|---|
| 弱类型：`res_type` / `field` 是字符串，拼错只在运行时暴露 | 两边都定义成**常量**，启动期校验白名单（§3），未登记直接 `30038` |
| 长度不齐：`name` 要 64、公告正文可能 2000 | 表统一 `VARCHAR(512)`，**各资源在 domain 里按自己的业务上限再收紧**（菜单 name ≤64）；要更长的正文（公告）用业务主表，不进这张表 |
| 没有外键：资源删了译文还在 | 资源删除时**同事务**调 `DeleteAll`（§5，规范硬性要求）；孤儿译文由月度清理任务兜底 |
| 单表增长 | 估算：菜单 120 + 字典 300 + 未来一万级 = 十万行内，`(res_type, field, lang, res_id)` 索引足够；到千万级再谈分区 |

## 2. 表设计

### 2.1 DDL（`config/sql/sys_i18n_text.sql`）

```sql
CREATE TABLE IF NOT EXISTS `sys_i18n_text` (
    `id`         BIGINT       NOT NULL COMMENT '雪花ID，应用侧生成',
    `res_type`   VARCHAR(32)  NOT NULL COMMENT '资源类型：menu / dict_item / dept / ...（domain/i18n 常量白名单）',
    `res_id`     BIGINT       NOT NULL COMMENT '资源主键',
    `field`      VARCHAR(32)  NOT NULL COMMENT '可翻字段：name / label / title（各资源的白名单内）',
    `lang`       VARCHAR(16)  NOT NULL COMMENT '已归一化语言标签：zh-CN / zh-TW / en-US（写入前经 i18n.ParseLang）',
    `content`    VARCHAR(512) NOT NULL COMMENT '译文；写入空串等价于删除该语言',
    `deleted_at` BIGINT       NOT NULL DEFAULT 0,
    `created_at` DATETIME(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
    `updated_at` DATETIME(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),
    PRIMARY KEY (`id`),
    -- 一个资源的某字段在某语言下只有一行；软删后同语言可重建
    UNIQUE KEY `uk_i18n` (`res_type`, `res_id`, `field`, `lang`, `deleted_at`),
    -- 列表页按 (资源类型 + 字段 + 语言) 批量取一页的译文，靠这把索引
    KEY `idx_i18n_batch` (`res_type`, `field`, `lang`, `res_id`)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4 COLLATE = utf8mb4_0900_ai_ci;
```

### 2.2 两把索引各自的用途

| 索引 | 谁在用 | 说明 |
|---|---|---|
| `uk_i18n` | 写入 upsert、详情查询 | 唯一性由它保证，重复保存必须**幂等更新**而不是插第二行 |
| `idx_i18n_batch` | 列表页批量加载 | `WHERE res_type=? AND field=? AND lang=? AND res_id IN (...)`：前三个常量、第四个走索引，一条 SQL 取一页译文 |

次序不是随手排的：把常量列放前面、`res_id` 放最后，才能让 `IN` 落在索引上；反过来（`res_id` 在前）会退化成多次回表。

### 2.3 为什么 `content` 是 512 而不是 TEXT

`TEXT` 会把这个列移出主表行外存储，每次读取多一次 IO，而这张表的读取频率是所有列表页。512 字符足够覆盖菜单名、字典项、部门名、岗位名、公告标题；真正需要长正文的场景（公告内容、富文本）应该有自己的业务表，多语言只是其中一列——**不要把这张表做成 CMS**。

## 3. 资源与字段的白名单

```go
// domain/i18n
type Resource string

const (
    ResMenu     Resource = "menu"
    ResDictItem Resource = "dict_item"
    // 新增资源在此追加，同时在 init 注册可翻字段
)

// translatableFields：**只登记允许翻译的字段**。
// path / code / value / icon / component / sort / status 这类标识字段根本不出现——
// 不是"约定不翻"，而是"登记了就会被拒"。
var translatableFields = map[Resource]map[string]int{ // 值为该字段的业务长度上限
    ResMenu:     {"name": 64},
    ResDictItem: {"label": 64},
}

// Validate 供 Save 前调用：res_type 未注册、field 不在白名单、超长 → 30038 / 30039
func ValidateTarget(r Resource, field string, content string) error
```

**为什么标识类字段必须"不登记"而不是"约好不翻"**：把 `path` 翻成中文，前端路由直接 404；把 `code` 翻译，权限匹配失效；把字典 `value` 翻译，历史数据按语言分裂。这三个事故都只需要一行错误的代码，用一个白名单把入口堵死，比写十行注释更可靠。

> **v1.2 演进**：上面的 `translatableFields` 已并入资源注册项 `registry[res].Fields`（§7.3），**机制完全不变**——仍是"未登记即拒绝"，只是同一个资源还要多带一个 `Resolver`。以 §7.3 的形态为准，本节保留原貌是为了说明白名单的由来。

## 4. 兜底与解析（唯一入口）

```
请求 lang（中间件解析一次，写入 ctx）
   ↓
sys_i18n_text (res_type, res_id, field, lang)   ← 命中即返回
   ↓ 未命中
主表默认语言列（sys_menu.name / sys_dict_item.label / ...，NOT NULL）
   ↓ 永远有值
完成 —— 不存在"返回空串"这条路径
```

四条硬规则：

1. **主表必须保留默认语言列**。它不是冗余，是兜底。只存子表的话，某门语言漏译时前端会出现空白菜单项，用户当 bug 报，排查半天发现是缺一行翻译。
2. **语言归一化统一走 `i18n.ParseLang`**（`en_us` → `en-US`，大小写不敏感）。不归一化就会出现同一语言两行数据、翻译永远查不到。
3. **每请求只解析一次 lang**，中间件写入 context，各层直接取。各层各自读 header、各自写 fallback 是这类机制的经典腐化方式。
4. **主表默认语言列与默认语言译文的关系**：主表列 = 默认语言（`site_lang`）的值。切换默认语言时**不自动改写历史数据**——那会让一批名称突然变成另一种语言，属于数据事故；由运营自行维护。

## 5. 读写 API（端口在 domain，实现在 infrastructure）

```go
type Repo interface {
    // Get 列表页唯一读法：一次 IN 查询返回 id → 译文。
    // 命中不到的不出现在 map 里，调用方回退主表列。
    Get(ctx context.Context, r Resource, ids []int64, field string, lang i18n.Lang) (map[int64]string, error)

    // GetMany 详情/编辑页用：id → field → lang → 译文，一次取回供表单回填。
    GetMany(ctx context.Context, r Resource, ids []int64, fields []string, langs []i18n.Lang) (map[int64]map[string]map[i18n.Lang]string, error)

    // Save 只覆盖「传入的语言」：texts 里没有的 lang 原样保留。
    // 某语言传空串 = 软删该语言（不能让空串盖掉兜底）。
    Save(ctx context.Context, r Resource, id int64, texts map[string]map[i18n.Lang]string) error

    // DeleteAll 资源删除时调用，必须与主表删除同一事务。
    DeleteAll(ctx context.Context, r Resource, id int64) error
}
```

三条约束：

- **禁止循环单查**。列表页 20 条 × 1 次 = 20 次往返，是列表接口变慢的第一原因，且很难在压测之外发现。`Get` 的签名刻意设计成批量，就是为了让"顺手写个 for 循环"变得别扭。
- **Save 的语义是"覆盖所传语言"**，不是"整表替换"。只传 `en-US` 时 `zh-TW` 必须原样保留——这与菜单 v0.4 的 `names` 语义一致，也让前端表单可以只提交改动过的 tab。
- **DeleteAll 必须同事务**。先删主表再删译文、中间失败，会留下指向不存在资源的译文；反过来则可能短暂丢兜底。一起提交，或一起回滚。

## 6. 接口契约（与具体资源解耦）

| 场景 | 形状 | 说明 |
|---|---|---|
| 列表 / 取项 | `[{id, name}]` —— **已解析的单字段** | 前端零翻译逻辑；不回 map |
| 详情 / 编辑 | `{id, name, names: {"en-US": "Users"}}` | `names` 供表单回填 |
| 写入 | `{name: "用户管理", names: {"en-US": "Users"}}` | 只覆盖所传语言 |
| 通用翻译接口（**本期落地**） | `GET/PUT/DELETE /api/v1/admin/i18n`（参数 `res_type/res_id/field/lang`，snake_case） | 后台"翻译"抽屉可泛化成一个组件，不必每个模块写一遍；实施记录见 §6.2 |

**为什么列表只回一个字段、详情才回 map**：让前端自己挑语言，等于把兜底逻辑复制到每个页面；复制三处以后就有三处不一致。这条在菜单设计里已经验证过（`sys_menu` 树只回一个 `name`），这里升为全局契约。

## 7. 译文管理（CRUD：增删改查）

> 一句话：**CRUD 的主键是四元组 `(resType, resId, field, lang)`，不是 `sys_i18n_text.id`。**

### 7.1 先确定"对什么做增删改查"

译文不是独立实体，它是**资源的附属属性**。所以 CRUD 有三种可能的操作对象，只有前两种成立：

| 视角 | 操作对象 | 谁在用 | 结论 |
|---|---|---|---|
| **资源视角** | 某资源的全部语言译文 | 模块维护者（菜单/字典编辑页的"翻译"tab） | ✅ 主场景 |
| **语言视角** | 某门语言的缺译条目 | 运营 / 翻译人员 | ✅ 新增场景（§7.6） |
| 记录视角 | 表里的一行（雪花 id） | 无人 | ❌ 明确拒绝 |

**拒绝"记录视角"的三个理由**：

1. 前端从不持有译文行 id——列表读到的是 `map[resId]string`，详情读到的是 `names`，id 是纯实现细节；把它暴露成主键，等于把内部结构写进契约；
2. `DELETE /texts/:id` 的语义是"删掉第 1234 行"，没人知道那是哪个资源的哪个语言——出事时无法审计、无法解释；
3. 最危险的：`POST /texts {resId: 9999}` 传个数字就能造一条指向不存在资源的译文，**孤儿数据一键量产**。§1.3 已承认"这张表没有外键"，若再把 resId 变成可自由填写的入参，等于放弃唯一的约束点。

### 7.2 增与改是同一个动作（幂等 PUT，不设 POST）

"新增一条译文"和"修改一条译文"，语义都是——**把四元组的值设为 X**。硬拆成 POST/PUT 会带来两个麻烦：

- POST 要判"已存在则报冲突"→ 前端必须"先查后写"，两次往返，中间还能被别人插队；
- 前端自己判断新旧（表单里空白→填了，算新增还是修改？），判断逻辑必然散落在每个页面。

所以只留 **`PUT`，幂等**：存在则更新，不存在则插入，重复提交同一个值结果不变。`POST` 只在"批量新建"才有意义，而译文没有"批量新建"的场景（新建 = 给某资源填语言，仍是 PUT）。

`uk_i18n` 是幂等的底层保障：重复保存必须是 upsert，不允许产生第二行活行（§2.2）。

### 7.3 资源注册表：把白名单常量升级成"带行为的注册项"

现有白名单（§3）只能回答"这个字段能不能翻"，回答不了三件 CRUD 必需的事：**这个 resId 存在吗、它叫什么、它归哪个权限管**。所以把它升级为注册表：

```go
// domain/i18n —— 白名单从 map[Resource]map[string]int 升级为注册项。
// 机制不变（未登记 = 禁止），只是每个资源额外挂一个 Resolver。
type ResItem struct {
    ID    int64
    Key   string // 人类可读标识：菜单 name / 字典项 value（列表与审计展示用）
    Value string // 默认语言下的字段值（翻译页的"原文"列）
}

type Resolver interface {
    // Exists 写入前校验目标资源存在（且未被逻辑删除）→ 否则 30040。
    Exists(ctx context.Context, id int64) (bool, error)
    // Snapshot 批量取 id → ResItem：一次 IN 查询，禁止循环（§5 同一条 N+1 红线）。
    Snapshot(ctx context.Context, ids []int64, field string) (map[int64]ResItem, error)
    // ListIDs 游标翻页取主表 id（afterID 递增），供缺译清单使用。
    // 只取 id，不取业务字段——通用层不该知道业务的筛选/排序规则。
    ListIDs(ctx context.Context, afterID int64, limit int) ([]int64, error)
    // PermWrite 该资源的写权限码（如 "menu:update"），见 §7.8。
    PermWrite() string
}

type Spec struct {
    Label    string         // 中文名（审计与前端页签）
    Fields   map[string]int // 字段 → 长度上限（原 translatableFields）
    Resolver Resolver
}

var registry = map[Resource]Spec{
    ResMenu:     {Label: "菜单", Fields: map[string]int{"name": 64}, Resolver: menuResolver{}},
    ResDictItem: {Label: "字典项", Fields: map[string]int{"label": 64}, Resolver: dictItemResolver{}},
}
```

`Exists` 是这次 CRUD 引入的**唯一新增约束点**。没有它，后台可以给任何数字造译文；有了它，`resId` 才从"用户可填的数字"变回"必须真实存在的主键"。代价是每种资源实现 4 个方法（约 30 行），换来的是孤儿译文在入口处就被挡住，而不是三个月后被人从列表里翻出来。

### 7.4 唯一真相：默认语言不进这张表

主表列（`sys_menu.name` / `sys_dict_item.label`）已经是默认语言的值（§4 规则 1）。如果允许译文表再存一份默认语言，就有**两份真相**：菜单改名走了主表、译文页改了 `zh-CN` 译文，两个值打架，读哪份取决于代码顺序。

所以定死两条：

| 方向 | 规则 |
|---|---|
| **读** | 默认语言**直接取主表列**，不查 `sys_i18n_text`；`texts` 里不返回默认语言的键 |
| **写** | 译文接口**拒收默认语言**（返回 `400`，msg 明确"默认语言请通过资源编辑修改"） |

`site_lang` 切换后，新默认语言若在译文表里有历史行，读路径按新默认语言走主表（主表行必然存在，§4 已有约束），旧行变成事实上的历史数据——这与 §4 规则 4"切默认语言不回写历史"一致。

> 用 `400` 而不是新业务码：这是"请求语义错"，不是业务规则失败，不值得占一个码段（码表膨胀本身就是维护成本）。

### 7.5 接口清单

```
GET    /api/v1/admin/i18n/meta?resType=menu                字段白名单 + 长度上限 + 已注册语言 + 默认语言（前端渲染 tab 用）
GET    /api/v1/admin/i18n/texts?resType=menu&resId=12      某资源的全部译文（详情/表单回填）
                                                           **resId 非必填（v1.4）**：省略即资源类型维度列表
GET    /api/v1/admin/i18n/texts?resType=menu&afterId=0&limit=50   译文总览（field 可选过滤；游标≤100 默认 50；缺译=空串；无 total）
PUT    /api/v1/admin/i18n/texts                            批量保存（只覆盖所传语言）
DELETE /api/v1/admin/i18n/texts?resType=menu&resId=12&field=name&lang=en-US   单条删除
POST   /api/v1/admin/i18n/texts/batch-delete               批量删除（上限 200，单事务）
GET    /api/v1/admin/i18n/pending?resType=menu&lang=en-US&afterId=0&limit=20  缺译清单
```

三处刻意取舍：

1. **不做 `/menus/:id/translations` 这类资源专属路由**：那要求每个资源重复实现一组 handler，正是通用表要消除的重复。通用路由 + `registry` 分发即可。
2. **PUT 的 `resType`/`resId` 放 body，GET/DELETE 放 query**：DELETE 带 body 会被部分网关/代理丢弃，不放 body 是保命习惯。
3. **`POST texts/batch-delete` 而不是 `DELETE` 带数组 body**：同上（body 会被丢），且批量删除要带回 `{deleted: N}` 的整体结果，POST 更自然。

> 注意：批量删除用的是**单事务全成功/全失败**，不是 FileManager 那种逐条部分成功——原因见 §7.7。
>
> **实施注记（2026-11-10，本族已全部落地）**：① 本族 JSON 字段名为 **camelCase**（如上表路径与响应示例），与其余模块 snake_case 的差异是有意保持与示例契约一致；② `resId` 按仓库语言中立约定回**雪花字符串**（示例中的 `12` 为示意）；③ `langs` 输出 = `i18n.Languages()` 字典序（前端渲染 tab 需要自定义顺序时可按 `defaultLang` 置顶重排）；④ `Resolver` 现注册 `menu`（label=菜单，PermWrite=menu:update 声明并预留）；`dict_item` **未注册**（字典模块未实现）——现阶段调 `/i18n/meta?resType=dict_item` 返回 `30038`（验收 17 的既有约定），字典 DAO 落地后取消 `RegisterI18nResolvers` 中的注释即可；⑤ 批量/单条删除按 §7.7 幂等（删不存在 = 200，`deleted` 计实际推进行数）。逐条实现对照见 §14 验收清单。

### 7.5.1 落地实现（与 §7.5 一一对应）

| 接口 | 处理链 | 关键点 |
|---|---|---|
| `GET meta` | `specOf`（未注册→30038）→ 静态视图 | 无资源存在性校验（meta 本身就是 tab 渲染依据） |
| `GET texts` | specOf → parseResID → `Resolver.Exists`（→30040）→ `Snapshot`（defaultValue）→ `Repo.GetMany`（texts） | 3 条 SQL 内回完；texts 无默认语言键、缺译=空串、langs 全量。**v1.4：resId 可选**——不传即列表模式（ListIDs + Snapshot + GetMany 共 ≤3 条 SQL，游标无 total；field 可选过滤，白名单外→30038；仍无默认语言键、缺译=空串），供译文总览页一次拉取 |
| `PUT texts` | specOf → `Exists`（**写前校验，不落行**）→ 字段白名单/语言/默认语言/内容逐项校验 → `Repo.Save` | 默认语言 → 400 + `i18n.defaultLang` 语言包文案；30035/30038/30039 分形返回；审计 `keys:["字段.语言"]` |
| `DELETE texts` | specOf → HasField → 必带 lang → `Repo.BatchDelete`（单元素复用批量通道） | 幂等；默认语言 400（译文表里无此行可删） |
| `POST batch-delete` | 逐项同上校验（任一失败整体拒绝）→ `Repo.BatchDelete` 单事务 | ≤200 否则 400；返回 `{"deleted": N}` |
| `GET pending` | specOf → `ListIDs` → `Snapshot` → `Repo.Get` 三次查询相减 | 默认语言 400（恒有主表值）；游标无 total |


`GET /texts` 响应（注意 `texts` 里**没有默认语言的键**，默认语言走 `defaultValue` 只读展示）：

```json
{ "status": 0, "msg": "ok", "data": {
    "resType": "menu", "resId": 12, "label": "菜单",
    "defaultLang": "zh-CN", "defaultValue": { "name": "用户管理" },
    "langs": ["zh-CN", "zh-TW", "en-US"],
    "texts": { "name": { "zh-TW": "使用者管理", "en-US": "User Management" } }
} }
```

`langs` 由服务端按 `i18n.Languages()` **补齐全量**，不是"只回已填的"。否则前端得自己 diff 语言注册表才能知道"还差哪门语言"——那等于在前端复制一份语言真相（§12 明确不做语言注册表，就是这个原因）。

`PUT /texts` 请求体（空串 = 删除该语言，与 `Repo.Save` 语义一致）：

```json
{ "resType": "menu", "resId": 12,
  "texts": { "name": { "en-US": "User Management", "zh-TW": "" } } }
```

### 7.6 缺译清单（运营视角）

这是 CRUD 里唯一"资源不知道怎么翻、只有翻译知道"的场景：给一门语言，列出还没翻的条目。三次查询完成，跨资源通用：

```
1. registry[resType].Resolver.ListIDs(afterId, limit)  → 一页主表 id（游标，无 total）
2. Resolver.Snapshot(ids, field)                       → id → {key, 默认语言值}
3. Repo.Get(resType, ids, field, lang)                 → id → 已有译文
   ↓
两集合相减 = 缺译；返回 {resId, key, field, source, content}
```

四个决策：

- **游标分页（`afterId`）而非 offset**：主表 id 单调递增，翻页期间新增/删除不会导致跳行重复；offset 在"边翻边补译"的操作流里必然出错。
- **不返回 `total`**：精确总数要 `count(主表)` + `count(有译文)` 两次聚合，而缺译数**每次保存都在变**——显示一个点开就过期的数字是负价值。前端显示"还有更多"即可。
- **不做关键词搜索**：搜"用户管理"要落到 `sys_menu.name`，那是业务字段，通用层不该知道。要搜索就在各模块自己的列表里搜，再从行内进翻译抽屉。
- **`status` 参数只留 `missing`**：`filled` 等价于该资源自己的列表，没必要在翻译页复刻一遍。

### 7.7 删除：三档粒度，全部软删，且幂等

| 粒度 | 接口 | 语义 | 谁调 |
|---|---|---|---|
| 单条 | `DELETE /texts?resType&resId&field&lang` | 删某资源某字段的某语言译文 | 翻译抽屉的"清空此语言" |
| 批量 | `POST /texts/batch-delete` | 一次删多条（上限 200），**单事务全成功或全失败** | 列表多选 |
| 随资源 | `Repo.DeleteAll`（内部） | 资源删除时同事务清空 | 菜单/字典的删除流程（§5） |

三点说明：

1. **删除幂等**：删一条不存在的译文返回成功。前端重复提交、两人同时清空同一语言都是常态，为此报错只会制造无意义的告警。
2. **批量不做"部分成功"**：译文没有引用约束、全是软删，一条 `UPDATE ... IN` 即可，全事务比 PartialSuccess 简单且可预期（与 FileManager 批量删除不同——那里有引用保护才需要逐条）。
3. **不提供"删除整资源译文"的独立接口**：那会造出"有资源但没译文"的状态，只剩兜底；要那么做应该走资源自己的保存流程，而不是在翻译页留一个语义模糊的按钮。

**复活语义**：不设 `restore` 接口，重新 `PUT` 即恢复。实现上会发生"插一条新活行、墓碑行保留"——这是 `uk_i18n` 含 `deleted_at` 的必然结果（软删行与活行的键不同，不冲突）。行为正确（读只取 `deleted_at = 0`），但墓碑会累积：**P2 加一个 30 天墓碑物理清理任务**（审计靠 `sys_oper_log`，不靠这张表里的墓碑）。

### 7.8 权限：译文接口就是"改名接口"

这是 CRUD 引入的**新攻击面**，必须说清：

- 改造前，译文只能随资源保存写入，天然受模块权限约束；
- 改造后，`PUT /i18n/texts?resType=menu` 实质上就是"改菜单显示名"。如果只校验一个笼统的 `i18n:write`，任何拿到翻译权限的人**就能改任意菜单名、任意字典项 label**——绕过模块自己的权限，且改名后前端菜单立刻变样。

所以写接口的校验是**两层**：登录态 + `registry[resType].PermWrite()` 声明的资源写权限（`menu` → `menu:update`，`dict_item` → `dict:update`）。

> **现状诚实说明**：项目目前还没有按钮级鉴权中间件（菜单 `code` 只做权限点标识，见菜单文档 §10）。所以 `PermWrite` 现在只能"声明并预留"，接口暂时只要求登录态。**不要把这条当成已生效的安全边界**——RBAC 上线时把它接到中间件上，一行即可生效；在那之前，译文管理页应只对超管开放。

### 7.9 写路径只有一条

```
资源编辑页保存 ─┐  主表 UPDATE + 译文 Repo.Save（同一事务）
翻译管理页保存 ─┴─→ Repo.Save(resType, id, {field: {lang: text}})
                    └ 空串 = 软删该语言（删除不另开写路径）
```

**禁止为 CRUD 另写一套写逻辑**。CRUD 层只做三件事：参数校验（§3 白名单）、`Resolver.Exists` 存在性校验、把请求体翻译成 `Repo.Save` 的形状。一旦出现第二条写路径，白名单校验、空串即删除、`uk_i18n` upsert、默认语言拦截这四条规则就得各写一遍，第三处必然漏。

### 7.10 审计与缓存失效

- **审计**：写操作登记 `OperMetaRegistry`，`module=i18n`，`action=text.save` / `text.delete`；`detail` 记 diff（键为 `字段.语言`）：`{"name.en-US": {"old": "Users", "new": "User Management"}}`。批量删除超过 2048 字符时截断并附计数（与操作日志 §4.6 的截断规则一致）。译文只软删，**不涉及 PhysDelete**，不需要整行快照。
- **缓存失效点**：§11 本期不缓存。将来加缓存时，失效入口有且只有两处——`Repo.Save`（含空串删除路径）与 `Repo.DeleteAll`；按 `(res_type, lang)` 整键失效，别按 id 精细失效——漏一个 id 就是"改了翻译不生效"的幽灵 bug。

## 10. 接入一个新资源要做的 6 件事

1. **主表保留默认语言列**（`name` / `label`，`NOT NULL`），它是兜底；
2. **在 `domain/i18n` 注册 `ResType` + 可翻字段白名单**（含长度上限，落在 `registry[res].Fields`）；
3. **实现 `Resolver`**（`Exists` / `Snapshot` / `ListIDs` / `PermWrite`）——不实现则译文管理页看不到这个资源，也无法在写入时阻止孤儿译文；
4. **列表读取走 `Repo.Get`**（一次批量），详情走 `GetMany`；
5. **写入只覆盖所传语言**，空串 = 删除该语言；
6. **删除资源时同事务 `DeleteAll`**。

六条缺一条视为未完成。前五条漏了功能会错，第六条漏了会攒孤儿数据——而孤儿数据在三个月内没人发现。第 3 条是引入译文管理（§7）后新增的：白名单只管"能不能翻"，管不了"这个 id 存不存在"。

## 11. 缓存

**本期不缓存**：全表万行级，`idx_i18n_batch` 命中 <1ms，加缓存的失效复杂度远大于收益。

何时加：单次列表请求的译文查询成为 P95 瓶颈（一般要到几十万行 + 高 QPS）。届时按 `sys_config` 快照同一模式：`(res_type, lang)` 维度 30s TTL + 写后失效 + `atomic.Pointer` 读无锁，**禁止在 dao 层塞包级 map**。

## 12. 明确不做

- 不做翻译审批流 / 机器翻译（质量不可控，宁缺勿错；缺译回退默认语言）；
- 不做译文版本历史（要追溯用 `sys_oper_log` 的 Detail diff）；
- 不做语言注册表（语言集合 = `pkg/i18n.Registered()`，避免两处真相；`site_lang` 只决定默认语言）；
- 不翻标识类字段（`path` / `code` / `value` / `icon` / `component` / `sort` / `status`），白名单里根本没有它们；
- 不把 UI 文案入库（见 §0）；
- 不做按语言分表 / 分库；
- 不做 `TEXT` 长正文（公告内容这类走业务表自有列）；
- **不做以译文行 id 为目标的接口**（`PUT/DELETE /texts/:id`）：主键是四元组，理由见 §7.1；
- **不做跨资源关键词搜索 / 精确总数**：搜索要落到各业务主表的字段，通用层不该知道；缺译数每次保存都在变，`total` 是负价值（§7.6）；
- **不做译文级乐观锁**：同一四元组被两人同时编辑的概率极低，而加版本号会波及资源保存路径（§7.9 那条唯一写路径）；真出现丢失更新，按 `sys_oper_log` 的 diff 还原即可。触发条件：运营反馈同名译文的改动"莫名被覆盖"超过一次，再在 `Save` 上加 `updated_at` 比对。

## 13. 错误码

| code | 含义 | 备注 |
|---|---|---|
| 30035 | 语言不被支持（不在 `i18n.Registered()` 内） | **复用**菜单既有码，不重复申领 |
| 30038 | 翻译资源类型/字段未登记（不在白名单内） | v1.0 |
| 30039 | 译文超长或含非法字符（控制字符、`\x00`） | v1.0 |
| **30040** | **译文目标资源不存在**（`resType` 合法但 `resId` 在主表查无此行 / 已逻辑删除） | v1.2，`Resolver.Exists` 返回 false 时用 |

- **i18n 段为 30038~30040**，字典段从 **30041** 起（字典文档 §4），不冲突；
- 以下两类**不占业务码**，走通用 `400`（参数错误）：批量操作超过 200 条上限、`PUT` 时传了默认语言（§7.4 的"默认语言请通过资源编辑修改"）——它们是请求形状问题，不是业务规则失败；
- 删除不存在的译文**不报错**（幂等，§7.7），因此没有"译文不存在"的码；
- 按规范 §3.3：新码需 `pkg/code` 常量 → `msg.go` → `zh-CN` / `zh-TW` / `en-US` 三份语言包，**共五处同步**，缺一即交付不完整。

2. 未注册资源类型 / 未登记字段 → `30038`；超长译文 → `30039`；未注册语言 → `30035`；
3. `en_us` 写入后归一化为 `en-US`，且同语言不产生第二行（`uk_i18n` 生效）；
4. 列表接口对 20 条数据**只发 1 条**译文查询（日志或 SQL 计数验证，防 N+1 回归）；
5. 缺译时回退主表列，**永不返回空串**；某语言传空串保存 → 该语言译文被软删、回退生效；
6. `Save` 只传 `en-US` 时 `zh-TW` 译文不变；
7. 删除资源后，`sys_i18n_text` 对应行同事务软删（`deleted_at > 0`）；
8. 迁移后菜单树三语回归通过，字典 `?lang=` 三语回归通过。

**译文管理 CRUD（v1.2，§7）**

9. `PUT /i18n/texts` 传不存在的 `resId`（如 `999999`）→ `30040`，且库里**不新增任何行**（写前校验，不是写后清理）；
10. 同一四元组连续 PUT 三次 → 活行始终 1 条；`GET /texts` 只回 1 个值（幂等 upsert）；
11. `PUT` 的 `texts` 里含默认语言（如 `zh-CN`）→ `400` 且 msg 明确提示走资源编辑；`GET /texts` 的 `texts` 里**不含**默认语言键，默认值只在 `defaultValue` 出现；
12. `GET /texts` 返回的 `langs` 等于 `i18n.Languages()` 全量（新增一门语言后无需改接口即出现），`texts` 中缺失语言为空串而非缺键；
13. 删除某语言译文 → `GET` 回退主表默认值（不返回空串）；再 PUT 同语言 → 恢复且仅 1 条活行；
14. 重复 DELETE 同一条 → 两次都成功（幂等），不返回"译文不存在"；
15. 批量删除 200 条成功、201 条 → `400`；中途一条失败 → **全部回滚**，无部分成功；
16. `GET /i18n/pending` 对一页 20 条缺译数据只发 **3 条 SQL**（`ListIDs` + `Snapshot` + `Repo.Get` 各一条），回包无 `total` 字段；
17. 未实现 `Resolver` 的资源类型调 `meta` / `texts` → `30038`（不是 panic）；
18. 译文写操作在 `sys_oper_log` 记为 `module=i18n`，`detail` 含 `字段.语言` 级别的 old/new（若操作日志中间件已上线）。
