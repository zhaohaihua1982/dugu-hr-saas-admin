# 基础设施-数据文案多语言（i18n）设计

> 版本 v1.0 · 2026-11-10 · 统一取代 `sys_menu_i18n`（菜单）与 `sys_dict_item_i18n`（字典）两张分散子表
> 创建：2026-11-10 · 最后修改：2026-11-10
> 依赖：`pkg/i18n.Registered()`（语言注册表，唯一真相）、`sys_config.site_lang`（默认语言）
> 影响文档：`系统管理-菜单·配置·字典设计.md` §1.1、`系统管理-字典(sys_dict)设计.md` §7（两处改为指向本文）

## 0. 先划一条线：代码文案 vs 数据文案

多语言在这个系统里有两个完全不同的层，混在一起是绝大多数"多语言做成半吊子"的根因：

| | **代码文案** | **数据文案**（本文范围） |
|---|---|---|
| 例子 | 按钮"保存"、校验提示、错误码 30041 的 msg | 菜单名"用户管理"、字典项"员工花名册"、将来的部门名 / 岗位名 / 公告标题 |
| 谁维护 | 开发 | 运营 |
| 存哪 | 前端 `src/locales/*.ts`；后端 `pkg/i18n/locales/*.json` | **数据库**（本文的 `sys_i18n_text`） |
| 加一门语言的代价 | 改代码 + 发版 | 插行数据，即时生效 |
| 数量级 | 几百条，随功能增长 | 几千~几万条，随运营增长 |

**判据一句话：这份文案改了要不要发版？** 要 → 代码文案，进语言包；不要 → 数据文案，进这张表。

**最常见的误用**：把按钮文案塞进 DB。后果是改一个错别字要找运营、要走后台、还可能与已发布的前端版本不同步。反过来，把菜单名硬编码进前端语言包，运营连改个错字都得提需求——这两个方向的错都真实发生过。

## 1. 核心决策：一张通用翻译表，而不是每个资源一张子表

### 1.1 三个方案

| 方案 | 新增一个可翻译资源的成本 | 约束强度 | 机制一致性 | 判定 |
|---|---|---|---|---|
| 主表加 `name_en` / `name_ja` 多列 | 改表 + 改 PO/DTO/前端映射 | 强 | 差（列数随语言线性增长） | ❌ |
| **每个资源一张子表**（现状：`sys_menu_i18n`、`sys_dict_item_i18n`） | 建表 + 建 DAO + 写一遍 fallback + 前端再来一遍 | 强 | **靠人守，必然漂移** | ⚠️ 仅当资源只有 1~2 个 |
| **通用表** `sys_i18n_text` | 在 domain 注册一个常量 | 中（靠白名单 + 校验） | **机制唯一，不可能漂移** | ✅ 采用 |

### 1.2 为什么选通用表

本项目要翻的东西有个共同特征：**资源很多，每个只翻 1~2 个字段**。

- 菜单：40×3 行，字段只有 `name`
- 字典项：100×3 行，字段只有 `label`
- 将来：部门 `name`、岗位 `name`、公告 `title` + `content`、租户自定义字段的 `label`……

按"每资源一张子表"做，会得到 N 张字段几乎完全相同的表（`id, xxx_id, lang, 文案, deleted_at, created_at, updated_at`）+ N 份几乎相同的 DAO + N 处各自实现的 fallback。**这才是真正的重复**，而且一致性只能靠规范约束，实际项目里第三张表开始就必然写歪（漏兜底、漏归一化、漏软删）。

### 1.3 通用表的代价，以及对策

| 代价 | 对策 |
|---|---|
| 弱类型：`res_type` / `field` 是字符串，拼错只在运行时暴露 | 两边都定义成**常量**，启动期校验白名单（§3），未登记直接 `30038` |
| 长度不齐：`name` 要 64、公告正文可能 2000 | 表统一 `VARCHAR(512)`，**各资源在 domain 里按自己的业务上限再收紧**（菜单 name ≤64）；要更长的正文（公告）用业务主表，不进这张表 |
| 没有外键：资源删了译文还在 | 资源删除时**同事务**调 `DeleteAll`（§5，规范硬性要求）；孤儿译文由月度清理任务兜底 |
| 单表增长 | 估算：菜单 120 + 字典 300 + 未来一万级 = 十万行内，`(res_type, field, lang, res_id)` 索引足够；到千万级再谈分区 |

## 2. 表设计

### 2.1 DDL（`config/sql/sys_i18n_text.sql`）

```sql
CREATE TABLE IF NOT EXISTS `sys_i18n_text` (
    `id`         BIGINT       NOT NULL COMMENT '雪花ID，应用侧生成',
    `res_type`   VARCHAR(32)  NOT NULL COMMENT '资源类型：menu / dict_item / dept / ...（domain/i18n 常量白名单）',
    `res_id`     BIGINT       NOT NULL COMMENT '资源主键',
    `field`      VARCHAR(32)  NOT NULL COMMENT '可翻字段：name / label / title（各资源的白名单内）',
    `lang`       VARCHAR(16)  NOT NULL COMMENT '已归一化语言标签：zh-CN / zh-TW / en-US（写入前经 i18n.ParseLang）',
    `content`    VARCHAR(512) NOT NULL COMMENT '译文；写入空串等价于删除该语言',
    `deleted_at` BIGINT       NOT NULL DEFAULT 0,
    `created_at` DATETIME(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
    `updated_at` DATETIME(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),
    PRIMARY KEY (`id`),
    -- 一个资源的某字段在某语言下只有一行；软删后同语言可重建
    UNIQUE KEY `uk_i18n` (`res_type`, `res_id`, `field`, `lang`, `deleted_at`),
    -- 列表页按 (资源类型 + 字段 + 语言) 批量取一页的译文，靠这把索引
    KEY `idx_i18n_batch` (`res_type`, `field`, `lang`, `res_id`)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4 COLLATE = utf8mb4_0900_ai_ci;
```

### 2.2 两把索引各自的用途

| 索引 | 谁在用 | 说明 |
|---|---|---|
| `uk_i18n` | 写入 upsert、详情查询 | 唯一性由它保证，重复保存必须**幂等更新**而不是插第二行 |
| `idx_i18n_batch` | 列表页批量加载 | `WHERE res_type=? AND field=? AND lang=? AND res_id IN (...)`：前三个常量、第四个走索引，一条 SQL 取一页译文 |

次序不是随手排的：把常量列放前面、`res_id` 放最后，才能让 `IN` 落在索引上；反过来（`res_id` 在前）会退化成多次回表。

### 2.3 为什么 `content` 是 512 而不是 TEXT

`TEXT` 会把这个列移出主表行外存储，每次读取多一次 IO，而这张表的读取频率是所有列表页。512 字符足够覆盖菜单名、字典项、部门名、岗位名、公告标题；真正需要长正文的场景（公告内容、富文本）应该有自己的业务表，多语言只是其中一列——**不要把这张表做成 CMS**。

## 3. 资源与字段的白名单

```go
// domain/i18n
type Resource string

const (
    ResMenu     Resource = "menu"
    ResDictItem Resource = "dict_item"
    // 新增资源在此追加，同时在 init 注册可翻字段
)

// translatableFields：**只登记允许翻译的字段**。
// path / code / value / icon / component / sort / status 这类标识字段根本不出现——
// 不是"约定不翻"，而是"登记了就会被拒"。
var translatableFields = map[Resource]map[string]int{ // 值为该字段的业务长度上限
    ResMenu:     {"name": 64},
    ResDictItem: {"label": 64},
}

// Validate 供 Save 前调用：res_type 未注册、field 不在白名单、超长 → 30038 / 30039
func ValidateTarget(r Resource, field string, content string) error
```

**为什么标识类字段必须"不登记"而不是"约好不翻"**：把 `path` 翻成中文，前端路由直接 404；把 `code` 翻译，权限匹配失效；把字典 `value` 翻译，历史数据按语言分裂。这三个事故都只需要一行错误的代码，用一个白名单把入口堵死，比写十行注释更可靠。

## 4. 兜底与解析（唯一入口）

```
请求 lang（中间件解析一次，写入 ctx）
   ↓
sys_i18n_text (res_type, res_id, field, lang)   ← 命中即返回
   ↓ 未命中
主表默认语言列（sys_menu.name / sys_dict_item.label / ...，NOT NULL）
   ↓ 永远有值
完成 —— 不存在"返回空串"这条路径
```

四条硬规则：

1. **主表必须保留默认语言列**。它不是冗余，是兜底。只存子表的话，某门语言漏译时前端会出现空白菜单项，用户当 bug 报，排查半天发现是缺一行翻译。
2. **语言归一化统一走 `i18n.ParseLang`**（`en_us` → `en-US`，大小写不敏感）。不归一化就会出现同一语言两行数据、翻译永远查不到。
3. **每请求只解析一次 lang**，中间件写入 context，各层直接取。各层各自读 header、各自写 fallback 是这类机制的经典腐化方式。
4. **主表默认语言列与默认语言译文的关系**：主表列 = 默认语言（`site_lang`）的值。切换默认语言时**不自动改写历史数据**——那会让一批名称突然变成另一种语言，属于数据事故；由运营自行维护。

## 5. 读写 API（端口在 domain，实现在 infrastructure）

```go
type Repo interface {
    // Get 列表页唯一读法：一次 IN 查询返回 id → 译文。
    // 命中不到的不出现在 map 里，调用方回退主表列。
    Get(ctx context.Context, r Resource, ids []int64, field string, lang i18n.Lang) (map[int64]string, error)

    // GetMany 详情/编辑页用：id → field → lang → 译文，一次取回供表单回填。
    GetMany(ctx context.Context, r Resource, ids []int64, fields []string, langs []i18n.Lang) (map[int64]map[string]map[i18n.Lang]string, error)

    // Save 只覆盖「传入的语言」：texts 里没有的 lang 原样保留。
    // 某语言传空串 = 软删该语言（不能让空串盖掉兜底）。
    Save(ctx context.Context, r Resource, id int64, texts map[string]map[i18n.Lang]string) error

    // DeleteAll 资源删除时调用，必须与主表删除同一事务。
    DeleteAll(ctx context.Context, r Resource, id int64) error
}
```

三条约束：

- **禁止循环单查**。列表页 20 条 × 1 次 = 20 次往返，是列表接口变慢的第一原因，且很难在压测之外发现。`Get` 的签名刻意设计成批量，就是为了让"顺手写个 for 循环"变得别扭。
- **Save 的语义是"覆盖所传语言"**，不是"整表替换"。只传 `en-US` 时 `zh-TW` 必须原样保留——这与菜单 v0.4 的 `names` 语义一致，也让前端表单可以只提交改动过的 tab。
- **DeleteAll 必须同事务**。先删主表再删译文、中间失败，会留下指向不存在资源的译文；反过来则可能短暂丢兜底。一起提交，或一起回滚。

## 6. 接口契约（与具体资源解耦）

| 场景 | 形状 | 说明 |
|---|---|---|
| 列表 / 取项 | `[{id, name}]` —— **已解析的单字段** | 前端零翻译逻辑；不回 map |
| 详情 / 编辑 | `{id, name, names: {"en-US": "Users"}}` | `names` 供表单回填 |
| 写入 | `{name: "用户管理", names: {"en-US": "Users"}}` | 只覆盖所传语言 |
| 通用翻译接口（可选，P2） | `GET/PUT /api/v1/admin/i18n?resType=menu&resId=1` | 后台"翻译"抽屉可泛化成一个组件，不必每个模块写一遍 |

**为什么列表只回一个字段、详情才回 map**：让前端自己挑语言，等于把兜底逻辑复制到每个页面；复制三处以后就有三处不一致。这条在菜单设计里已经验证过（`sys_menu` 树只回一个 `name`），这里升为全局契约。

---

## 7. 前端契约

- **列表页不感知多语言**：字段已解析，直接渲染；
- **编辑页用同一个多语言表单组件**（按 `i18n.Registered()` 渲染 tab），不要在菜单页、字典页各写一套；
- **请求带 lang**：取自本地 `dugu-lang`，由 axios 拦截器统一注入，页面不手写；
- **禁止前端做 lang→文案映射**：那等于第二份字典，必然与后端不一致。

## 8. 从两张旧子表迁移

### 8.1 映射

| 旧表 | `res_type` | `field` | 备注 |
|---|---|---|---|
| `sys_menu_i18n` | `menu` | `name` | 菜单 v0.4 已实现（含 zh-TW 存量补齐 `application/menus/backfill.go`） |
| `sys_dict_item_i18n` | `dict_item` | `label` | 字典设计 v1.1 刚定，尚未实现 |

### 8.2 步骤

1. 建 `sys_i18n_text`（`config/sql/sys_i18n_text.sql`）；
2. **一次性回填**（幂等，`INSERT IGNORE`，`deleted_at` 原样透传）：

```sql
-- 实际由迁移程序执行：逐行生成雪花 ID（不要用 seed 9e15 段，那是初始化数据的专用段位）
INSERT IGNORE INTO `sys_i18n_text` (`id`, `res_type`, `res_id`, `field`, `lang`, `content`, `deleted_at`)
SELECT /* 雪花ID，由迁移程序注入 */, 'menu', `menu_id`, 'name', `lang`, `name`, `deleted_at`
FROM `sys_menu_i18n`;
```

3. **切换读路径**：`domain` 的 `DisplayName` / `DisplayLabel` 签名不变，只把内部 Loader 换成通用 `Repo`——这也是当初坚持"单一解析入口"的回报，调用方一行不用改；
4. **切换写路径**：保存时按 `{field: {lang: text}}` 结构交给 `Save`；
5. **校验**：旧表与新表行数/内容抽样比对；菜单树 `?lang=zh-TW`、`?lang=en-US` 回归；缺译回退用例重跑；
6. **旧表退役**：本例按用户裁定**迁移当版即 DROP**（未按"保留一个版本只读"执行——回填程序在行数核对一致后才 DROP，不一致 fail-fast 保留旧表下次重试；实现见 `infrastructure/db/migrate.go backfillAndDropMenuI18n`）。

### 8.3 迁移结果（已完成，窗口关闭）

- 2026-11-10 执行：`sys_menu_i18n` 存量 **122 行**（含 zh-TW 存量补齐行与 2 条软删历史，`deleted_at` 原样透传）迁入 `sys_i18n_text`；行数核对一致后旧表 **DROP**，`config/sql/sys_menu_i18n.sql` 删除；
- 读/写/删路径已全部切换至 `domain/i18n.Repo`（菜单树 1 条批量译文查询，无 N+1）；接口契约（`?lang=` / `names`）零变化，三语言回归通过；
- 幂等保证重现安全：老库自动完成回填+校验+退役，全新库直接跳过（旧表不存在即 no-op）；
- 软删透传：资源删除后由 `deleteAllTx` 同事务软删统一表译文，行为与旧表等价。

## 9. 接入一个新资源要做的 5 件事

1. **主表保留默认语言列**（`name` / `label`，`NOT NULL`），它是兜底；
2. **在 `domain/i18n` 注册 `ResType` + 可翻字段白名单**（含长度上限）；
3. **列表读取走 `Repo.Get`**（一次批量），详情走 `GetMany`；
4. **写入只覆盖所传语言**，空串 = 删除该语言；
5. **删除资源时同事务 `DeleteAll`**。

五条缺一条视为未完成。前四条漏了功能会错，第五条漏了会攒孤儿数据——而孤儿数据在三个月内没人发现。

## 10. 缓存

**本期不缓存**：全表万行级，`idx_i18n_batch` 命中 <1ms，加缓存的失效复杂度远大于收益。

何时加：单次列表请求的译文查询成为 P95 瓶颈（一般要到几十万行 + 高 QPS）。届时按 `sys_config` 快照同一模式：`(res_type, lang)` 维度 30s TTL + 写后失效 + `atomic.Pointer` 读无锁，**禁止在 dao 层塞包级 map**。

---

## 11. 明确不做

- 不做翻译审批流 / 机器翻译（质量不可控，宁缺勿错；缺译回退默认语言）；
- 不做译文版本历史（要追溯用 `sys_oper_log` 的 Detail diff）；
- 不做语言注册表（语言集合 = `pkg/i18n.Registered()`，避免两处真相；`site_lang` 只决定默认语言）；
- 不翻标识类字段（`path` / `code` / `value` / `icon` / `component` / `sort` / `status`），白名单里根本没有它们；
- 不把 UI 文案入库（见 §0）；
- 不做按语言分表 / 分库；
- 不做 `TEXT` 长正文（公告内容这类走业务表自有列）。

## 12. 错误码

| code | 含义 | 备注 |
|---|---|---|
| 30035 | 语言不被支持（不在 `i18n.Registered()` 内） | **复用**菜单既有码，不重复申领 |
| 30038 | 翻译资源类型/字段未登记（不在白名单内） | 新增 |
| 30039 | 译文超长或含非法字符（控制字符、`\x00`） | 新增 |

30040 段归字典（30041~30049），不占用。按规范 §3.3：新码需 `pkg/code` → `msg.go` → 双语言包四处同步。

## 13. 验收

1. `go build ./...`、`go vet ./...` 通过；
2. 未注册资源类型 / 未登记字段 → `30038`；超长译文 → `30039`；未注册语言 → `30035`；
3. `en_us` 写入后归一化为 `en-US`，且同语言不产生第二行（`uk_i18n` 生效）；
4. 列表接口对 20 条数据**只发 1 条**译文查询（日志或 SQL 计数验证，防 N+1 回归）；
5. 缺译时回退主表列，**永不返回空串**；某语言传空串保存 → 该语言译文被软删、回退生效；
6. `Save` 只传 `en-US` 时 `zh-TW` 译文不变；
7. 删除资源后，`sys_i18n_text` 对应行同事务软删（`deleted_at > 0`）；
8. 迁移后菜单树三语回归通过，字典 `?lang=` 三语回归通过。
